# sansi-erhouxing：动手改之前先看全局

**一句话**：改任何已存在的东西之前，先看整体，再动手。软约束，不阻断交付，只挡在"要动手改"这个动作前面。

---

## 问题：老在犯的一个通病

写代码、写文档、更新技能，都会碰到同一种情况：

- Review 说这一段有问题，直接冲上去改那一段。
- 静态检查报了一个点，直接把那个点改掉。
- 用户说"加一节"，直接挂在文末。
- 上一 commit 删掉的兜底，review 说要加回来，直接加回去。

看着都合理，合起来就是**补丁摞补丁**。每个补丁本身没错，但每个补丁都只看局部，不看整体，几轮下来整篇稿子/整套代码开始走样，读者感受到的是"越改越散"。

我把这类反模式起了个名叫**丢西瓜捡芝麻**：修一个小问题，引发一个更大的问题。

代码场景最常见：上一 commit 刚删的兜底，review 说要保留，你直接加回来，结果原本 fix 的 bug 复现了。上一 commit 删兜底，恰恰是为了让某类错误浮出来。**不看 MR 的历史 commit，只看当前 review comment，就是典型症状**。

文档场景一样犯：改一节的时候不通读全文，新写的和第四节讲的东西大量重叠；用户说"加一节"，不管骨架直接挂末尾，读者读到那里发现和主线断了气。

**问题的根子只有一句话**：改动的时候只盯局部，没有全局视角。

---

## 想法：能不能把"三思"变成 Agent 能跑的流程

"改之前先想一下"是老智慧，不是新发明。经验丰富的工程师、编辑，天然会这么做，先通读、再动手，像老木匠上手之前先摸一遍料。

但对 AI Agent 来说，这套习惯不是天生的。**Agent 的默认行为是"看到一个点就修一个点"**，在 review 反馈或 lint 报告这种"命中即修"的场景下，补丁摞补丁的倾向比人更强。

所以想法就一句：**把这套"先想清楚再动手"的老智慧，做成 Agent 可执行的自律流程**。不加一个人在中间盯着，也不阻断交付，只挡在"要动手改"这个动作前面，让 Agent 先停一下、看整体、列影响面、再动。

---

## 业界怎么讲这件事

动工前翻了文献，发现这条常识其实早有几条经典工程原则撑腰，只是以前靠老师傅心口相传，很少落成 Agent 执行检查点：

### Shotgun Surgery（Martin Fowler，《Refactoring》）

一处职责散落在多个文件时，漏改其中一角就会整体错位（见 [Shotgun surgery](https://en.wikipedia.org/wiki/Shotgun_surgery) 与 [Eliminating Shotgun Surgery](https://bito.ai/blog/eliminating-shotgun-surgery/)）。落实到流程里，就是动笔前必须先对齐两栏影响面。

### Chesterton's Fence（G.K. Chesterton，1929）

看到路中间有道不明不白的栅栏，别急着拆，先查明白当初为什么立在那儿。对应的就是检查历史 commit 与前一次删改理由，免得手快把旧坑重新挖开。

### Kent Beck：先让修改变简单，再动手改

2012 年推文原话：「For each desired change, make the change easy (warning: this may be hard), then make the easy change.」当前结构下改起来特别拧巴时，先把结构理顺再改核心逻辑，别在旧壳子上硬绕弯。

### Outline-First（写长稿的骨架优先）

写作与设计一致公认先搭好骨架再填血肉；改局部时必须重扫大纲，不靠硬添过渡段维持虚假顺滑。

### 另外两个容易混淆的相邻概念

- **Band-Aid Fix（打补丁）：**只遮症状不问根因，判据就是修法带来的风险大于问题本身。
- **Root Cause Analysis（根因分析）：**先问清楚问题从哪来的，而不是直接空判一个 null 糊弄过去。

## 结论：三步硬约束 + 骨架优先

四条业界思路都是心法，给人看的。做成 Agent 流程，得能被机械执行。落成三步：

### 通读整体

按载体走：

| 改动场景 | 通读到哪里 | 过关标准 |
|-|-|-|
| 代码单点修 bug | 所在模块、本 MR 全部提交、diff 与直接调用方 | 说得出这段代码的职责以及本 MR 前序改动意图 |
| 代码加新功能 | 整体架构和仓库里已有相似实现 | 查清有没有现成轮子可复用再定新建 |
| 文档局部润色或加节 | 全文目录骨架及前后承启段落 | 确定新内容能否顺着主线接上去，接不上就调骨架或放弃 |
| 更新已有技能 | 主文件、全量 references 和历史发版记录 | 找到原规则意图，不叠冲突的新补丁 |
| 方案或配置微调 | 全份配置以及上游引用入口 | 说得出改这一处后会连带波及谁 |

**不到位不许下笔**。

### 列影响面

两栏：

- **这次要动的点**：准备改/新增的具体位置
- **跟这个点相关的既有逻辑**：同一模块的相邻代码、本次 MR 里改过的相关处、文档骨架里的前后章、已有的类似机制、依赖此处的下游

**相关的没列全，不许下笔**。

### 动手前先问三句

一条一条问，一条不过就停：

1. **这个位置历史上动过吗（Chesterton's Fence）？**如果刚改过或刚删过，先查 commit 与评审记录，别把刚拔掉的旧兜底又塞回去。
2. **修法引入的风险是否比原问题更大（Band-Aid Check）？**大于就停手换思路或先重构。
3. **这么改会不会撕裂整篇结构连贯性？**拼不进主线就退回骨架重排，不准打补丁。

**三问任一不过，回退到"不改"或"重设计"，不许硬修**。

### 骨架优先（文档类专用）

写长文或大改时，务必先把每一节一句话的主旨顺直、最后再添过渡句：

1. 先列骨架：每一节一句话观点，顺一遍能不能立住、之间有没有承启
2. 骨架顺了再填内容
3. 内容都填完最后加过渡
4. 改了任何一节，回骨架重扫一遍。骨架被破坏了就重来，不许打补丁维持假连贯

代码有对应做法：改动前先问"先重构让改动变容易，还是直接改"，绕来绕去就先调结构。

### 力度与豁免

**软约束**，不阻断交付：

- **重档（生产代码 MR、对外文档、已发布技能）：**完整走完三步，把分析留档。
- **中档（内部文档、工具脚本、个人笔记）：**跑通流程，口头说明影响即可。
- **轻档（错字、拼写、纯格式微调）：**可跳过，只需顺手确认这真只是笔误。

**豁免**：一次性丢弃脚本、明确探索性代码、纯一句话答疑，可以跳过。豁免要在心里对自己说一句"这是探索，不是产出"，能说出口才算数。

## 一次实战：三思而后行修好好说话

技能刚做完，拿隔壁 haohao-shuohua v3 试刀。

之前另一个 AI review 好好说话时报了 6 个问题：

1. 主文档写「两遍回读」，`workflow.md` 却写「三遍」
2. 主文档说「五层扫描」，`workflow.md` 仍写「四层」
3. `description` 从 81 字膨胀到了 255 字
4. 文档里提到 `scan.sh`，仓里压根没这个文件
5. 长句没气口被规则漏掉
6. 标题举例意外命中了量词标题禁令

没先通读直接改这六点十有八九踩坑。跑完「通读全文加影响面和三问」之后，处置完全分出了高下：

| 待处理点 | 只盯局部的做法 | 看过全局后的做法 |
|-|-|-|
| 1. 两遍与三遍不一致 | 改成统一三遍 | 对齐修改（属于单纯漏同步） |
| 2. 四层与五层不一致 | 改成统一五层 | 对齐修改（新增层级后未同步） |
| 3. description 涨到 255 字 | 砍回 81 字 | 不改（刻意加宽了触发面，回退等于丢能力） |
| 4. 引了不存在的 `scan.sh` | 硬补一个脚本 | 保留口头命令指引（加脚本反而牵扯沙箱路径风险） |
| 5. 长句规则漏网 | 塞进硬门禁规则表 | 挪去节奏校验文档，免得破坏零容忍列表的清晰度 |
| 6. 正则误报 | 只调那一条正则 | 正则放行豁免加上反例微调双管齐下 |

**三思避免了三个补丁：**

- **问题 3：**如果把扩出来的触发描述砍回 81 字，触发面就直接丢了。
- **问题 4：**硬新建脚本会撞进路径与沙箱权限坑，不如直接改提示词。
- **问题 5：**硬把节奏规则写进硬门禁表，会把原本的三条零容忍边界搞乱。

改完还回骨架重扫了一遍。主文件里"命令行扫"的措辞和 quick-scan-regex.md 对齐，"五层扫描"和 workflow.md 对齐，反例标题改完没有反向引用被打断。**5 处动刀加 1 处豁免，一次跑通，没打补丁**。

## 跟隔壁技能的关系

- **内容与文风技能：**例如好好说话、淬火、汤山体，接到修改已有稿件时先过一遍整体骨架。
- **技能更新（`skill-creator`）：**调整现成技能前先看上下引用。
- **Code Review 与静态检查：**它们负责指出错处，这个技能只管动手修之前看大局。

依赖是单向的：产出型技能在改稿前调三思而后行，它自己不反向耦合具体内容模板。

---

## 把这几条原则收成一句话

Shotgun Surgery 提醒列清影响面，Chesterton's Fence 要求动前先查历史，Kent Beck 教人先调结构别硬扛，Outline-First 守住骨架顺序。四件老手习惯写成 Agent 前置清单，只挡在动手前那一秒，不阻塞正常交付。
