# 让你的大模型支持视频：Video Reader

> 让看不了视频的大模型，能"看懂"一段视频。

<callout emoji="🎼">
**安装链接：**AgentBuddy    Mira
</callout>

> **如果平台拦截视频上传，压成 zip 再传**
> 
> 像 Mira 等平台经常禁止直传 `.mp4` 或 `.mov`，直接把录屏压成 `.zip` 发上来，上层模型会自动先解压再调用脚本分析。

## 它能帮你做什么

查问题时 QA 或客诉经常直接甩过来一条录屏，但多数文本或图文大模型没法直接读视频。静态 UI 错截一两张图还能看懂，遇到滑动卡顿、回弹闪烁这类动态连续问题，人很难光靠文字说清前后几帧的变化。

于是干脆写了个脚本工具：把视频按动态情况聪明地抽成关键帧喂给大模型，模型就能顺着帧和时间线自己往下查。

## 不就是抽帧吗？

是，但有一些小技巧

### 解决的两个关键难题

直接均匀抽帧有两个致命问题，这个技能专门把它们解掉：

| 难题 | 朴素做法 | 本技能的解法 |
|-|-|-|
| **上下文爆炸**：20 秒视频均匀抽成 20 张图全塞给模型，又贵又看花眼 | 硬塞 + 靠大窗口扛 | 只在"有动作"的地方抽帧，静止段整段折叠，一帧不抽 |
| **谁来挑关键帧**：让模型先把每帧看一遍才知道哪帧重要，等于没省 | 模型逐帧看 | **纯代码用帧差挑帧，零 token**，模型只看挑完的结果 |

帧差就是在 CPU 上算相邻两帧画面的像素变化量，不经大模型。画面不动直接跳过，画面一动就开始密集取样。

![这张图将两种抽帧方式做了直观对比：左侧是均匀抽帧，沿时间轴均匀抽取画面样本，最终漏掉了红框标注的异常关键画面，无法捕捉特殊事件。右侧是运动感知抽帧，依托纯代码计算帧间像素变化判断画面动态，在画面静止的时段直接跳过无需抽帧，仅在画面有动作活动的时段密集抽帧，最终完整保留了全部关键过程。图中间的卡通机器人手持放大镜点明该抽帧模式的核心逻辑：先用纯代码定位画面动态区域，再筛选出关键画面，比逐帧查看视频更节省资源，筛选结果也更精准。](/assets/content/video-reader/sync-03.webp)

> 一句话：**通用大模型靠"塞得下"，我们靠"挑得准"。而挑准这步是免费的。**

### 整体流程：先粗后细，由大模型自己驱动

![这张图直观呈现了Video Reader“先粗后细、由大模型驱动”的核心处理流程：上方的“scan粗扫全片”环节以10fps的算力仅做轻量计算，生成全片运动时间线，自动定位出07.2到08.0秒的可疑区间；随后流程向下流转进入下方的“zoom局部下钻”环节，该环节以8fps的密集采样率针对可疑区间逐帧解析，依次捕捉面板展开、开始上滑、越过吸附位、继续上行、07.84秒回弹的完整动作细节。图旁搭配持放大镜的卡通机器人形象，呼应了该方案精准筛选关键帧、无冗余算力浪费的特性。](/assets/content/video-reader/sync-04.webp)

很多情况下模型光看 `scan` 吐出的文字时间线，就已经知道问题大概率卡在哪两秒，连粗扫帧都不用全部看完。

### 帧差全链路：一帧是怎么被判成"动 / 不动"的

上面说靠帧差挑关键帧，实际全由纯 CPU 数学脚本跑完这六个步骤，全程不花大模型一个 token：

![这张图直观展示了帧差全链路判断帧动/不动的完整流水线，顶部蓝色栏明确标注“整条链路只做数学，不碰大模型”，点明该流程全程仅由CPU数学脚本运行、不消耗大模型token的核心特性。流水线从最左侧的原始帧输入开始，依次经过运动指纹、运动分、自动阈值、合并停顿、折叠静止段、输出关键帧六个处理环节，最终在最右侧输出运动时间线，完整呈现了纯靠帧差逻辑筛选关键帧的全流程步骤。](/assets/content/video-reader/sync-05.webp)

#### 环节一：先压成 16×16 的亮度指纹

脚本不拿两帧原图直接做差，而是先把每帧"压"成一个便于比对的指纹（`motion_signature`），三步走：

1. **转灰度**：运动检测只关心亮度变化、不关心颜色，把 BGR 三通道降成单通道灰度，先做一次 3→1 的降维。
2. **高斯模糊**：用一个高斯核抹平细节，吸收压缩视频的块效应（马赛克）和高频噪点，避免它们被误当成"运动"。
3. **缩成 16×16 网格**：用 `INTER_AREA`（区域平均）把整帧缩成 16×16=256 个小块，每个块代表原图一片区域的平均亮度。这就是文档反复提到的"**分块比对**"。

缩小分块主要为了扛翻拍抖动。用户常拿另一台手机翻拍屏幕，难免手晃反光；若按逐像素算差，一点点位移就满屏误报。缩成 16×16 网格等于拿细部空间精度换抗抖能力，只有面板滑出之类大面积改动才会算进变化分。

#### 环节二：计算运动分

拿到相邻两个采样点的指纹后，运动分就是它们逐块之差取绝对值再求平均（MAD，Mean Absolute Difference）：

$$score = \frac{1}{N}\sum_{i=1}^{N}\left| s_i - s_i' \right|$$

其中 $s_i$ / $s_i'$ 是当前帧、上一帧第 $i$ 个块的灰度值，$N=256$。分数范围 0\~255，越大代表画面动得越凶。选 MAD 而不是结构相似度（SSIM）或直方图，是因为我们只要"动没动"这个粗判断，MAD 在 CPU 上一行 numpy 就算完，最轻、最快，够用即可。

#### 环节三：自动阈值，用中位数画分界线

不同视频亮度、录制方式差异很大，写死一个阈值必然在某些视频上失灵。所以阈值是自适应估算的（`auto_threshold`）：

$$thr = \max\left(0.8,\ 0.5 \times \mathrm{median}\left(\{\,s : s > 0.01\,\}\right)\right)$$

两个设计点：

- **用中位数，不用均值**：中位数抗离群值。视频里偶尔一次切场景会产生一个极大的运动分，把均值整体拉高；中位数几乎不受这种孤立尖峰影响，更能代表"这段视频日常的运动量水位"。取中位数的一半作分界，让略高于日常波动的帧被判为"动"。
- **为什么要有 0.8 这个地板**：纯静态视频（比如全程对着一张桌子）里，中位数本身极小，$0.5 \times median$ 会低到把传感器噪点都当成运动，判出满屏假活动段。地板 0.8 保证"必须动到一定程度才算动"，把静态视频的噪点挡在门外。

#### 环节四：分段，把离散点并成连续区间

拿着一串离散采样点，`segment_motion` 顺着扫一遍，按「运动分大于等于阈值」标成 active 或 static，标签一变就收成 `(start, end, type, peak)` 区间，记好峰值留给时间线汇总。

#### 环节五：合并碎片，别让手势中途的停顿剁碎时间线

连续手势里手指短暂一顿，直接分段会切出一大堆几十毫秒的静止碎片。`merge_short` 先清理掉这些毛刺：

- **吞掉短静止段：**夹在两个活动段之间且短于 `min_static`（默认 0.4 秒）的短停顿直接并回活动段，手势中途一停不值得切开。
- **合并相邻同类段：**吞并之后再把紧挨着的同属性段落顺手接成一条。

结果是一条干净、连贯的运动时间线，而不是被无意义停顿切碎的锯齿。

#### 环节六：智能抽帧，静止段全跳过、活动段保底取样

时间线划分完，`scan` 对静止段一帧不抽（只在文本时间线里记一行静止），只对活动段按密度均匀取帧，每段至少保留首、中、尾三帧避免漏掉起止瞬间。

### 两个采样率的解耦：分析要密，输出要稀

脚本里有两个容易混淆的"每秒几帧"，它们服务于完全不同的目的，被刻意分开：

- **分析采样率**（`analyze_fps`，默认 10）：只用来算运动时间线，不落盘任何帧。它要足够密，才能准确划出活动段的边界。
- **输出抽帧密度**（`--density`，scan 默认 2、zoom 默认 8）：真正落盘、喂给模型看的帧密度，稀疏即可。

一句话概括：**分析用高采样率求时间精度，输出用低密度省 token**。把"算得准"和"喂得省"这两个诉求解耦，是这套流水线省钱的关键之一。

### 工程细节

- **沙箱环境锁单线程：**OpenCV 与 FFmpeg 默认起很多线程，在受限沙箱会报创建线程失败。脚本在 `import cv2` 之前先把 `OPENCV_FFMPEG_THREADS`、`OMP_NUM_THREADS`、`OPENBLAS_NUM_THREADS` 设为 1 并调用 `cv2.setNumThreads(1)`。
- **标准输出与日志分流：**`stdout` 只打干净 JSON 供下游解析；人类可读时间线、进度与报错全走 `stderr`，避免污染管道数据。
- **恒定内存开销：**分析期逐帧顺序流过，内存里始终只留当前帧与上一帧两枚 16×16 指纹；处理几分钟视频也不会爆内存。

## 更多实现细节

### 环境依赖

- Python3 + `opencv-python-headless` + `numpy`（OpenCV 自带视频解码，**不依赖系统 ffmpeg**）
- `matplotlib`（仅 `--debug` 模式画曲线图时需要）
- **依赖自愈**：脚本启动时会自动检测缺失的依赖并尝试安装（`pip install --user --break-system-packages`，不污染系统环境），正常无需手动准备。仅当自动安装失败时，才会提示手动执行：`pip install --user --break-system-packages opencv-python-headless matplotlib`

### `scan`：先粗扫整段视频

```Bash
python3 scripts/video_frames.py scan <视频路径>
```

跑完会吐出运动时间线、活动区间、帧路径与秒数 JSON，同时把给人看的摘要打在 stderr。

| 参数 | 用途 | 默认值 |
|-|-|-|
| `--start / --end` | 只扫指定时间段 | 全片 |
| `--density` | 活动段每秒抽帧密度 | 2 |
| `--max-width` | 限制输出宽度省 token（0 为不缩放） | 900 |
| `--threshold` | 判定为运动的阈值 | 自动估算 |

> 性能特点：只从起点寻址一次后按顺序跳帧解码，长视频不会因频繁随机 seek 卡死；每约 5 秒输出一行进度。

### `zoom`：对可疑片段加密抽帧

```Bash
python3 scripts/video_frames.py zoom <视频路径> --start 10.0 --end 12.0 --density 8
```

看手指刚抬起或闪烁那一刻，可以把 `--density` 提到 12 到 15、区间缩到半秒内。

### `grid`：九宫格一图扫全片

![这张图直观演示了Video Reader的grid九宫格功能的工作流程：左侧展示了时长16秒的示例录屏视频素材，箭头指向带有循环标识的卡通机器人代表的处理模块，再通过箭头引出右侧的功能效果区域。该区域以3行3列的九宫格形式排列，共9张拼接后的视频帧图，每格左上角清晰标注对应秒数，依次覆盖00:00到00:16的采样时刻。图的底部配有说明文字，点明该功能可通过单张拼接图完整展现整段视频的节奏，支持先概览全片再缩小排查范围，契合相关文档中通过拼帧大图缩减token开销、方便快速定位目标时段的特性说明。](/assets/content/video-reader/sync-06.webp)

把整段视频（或某区间）均匀取帧拼成一张大图，每格左上角标好秒数。模型读这一张图就能看清全片节奏，省 token 还好定位，锁到可疑那一格后再用 `zoom` 放大。

```Bash
python3 scripts/video_frames.py grid <视频路径>
python3 scripts/video_frames.py grid <视频路径> --rows 4 --cols 4 --start 0 --end 30
```

- `--rows/--cols`：网格行列，默认 3×3；`--cell-width` 每格宽默认 320。
- 输出 JSON 里 `grid_path` 是拼好的大图，`cells[]` 是每格的秒数/行列号。
- 和 scan 互补：scan 的运动时间线擅长"哪几秒在动"，grid 擅长"整段长啥样"。仍用 OpenCV 自拼，不依赖系统 ffmpeg。

### `transcribe`：可选的语音转写

画面看不到、只能听到的信息（旁白、客诉口述、报错语音），用这个补。**可选软能力，缺依赖只提示并跳过，不影响 scan/zoom。**

```Bash
python3 scripts/video_frames.py transcribe <视频路径> --model turbo
```

- 依赖：系统 `ffmpeg`（抽音轨）+ `openai-whisper`（pip 包，含 torch 较重，脚本"用到才按需装"）。任一缺失会打印安装方法并以退出码 4 跳过。
- 输出：stdout 是 JSON（`text` 全文 + `segments` 带时间戳分段），stderr 是逐段带时间戳文字。
- 用法：把转写时间戳和 `scan` 的画面运动时间线对齐，能更准说出"第 X 秒画面在做什么、同时说了什么"。无音轨的纯录屏会自动跳过。

### `--debug` 调试模式（默认关闭）

平时不用开。调试技能本身、或想搞清楚"为什么这段被判成静止 / 运动"时加上：

```Bash
python3 scripts/video_frames.py scan <视频路径> --debug
```

开了之后：

- 帧存到**当前目录的 `video_reader_debug/<视频名>_<模式>/`**，稳定可复查（默认是随机临时目录，读完即弃）。
- 额外产出两份调试产物：

  - `_debug/motion_data.json`：每个采样点的时间 + 运动分、阈值、分段结果。
  - `_debug/motion_curve.png`：帧差曲线图，带阈值线和活动段底纹。看这张图就能一眼判断阈值定得对不对、活动段有没有漏判误判，据此调 `--threshold`。

> 临时帧清理：非 debug 模式下帧写入系统临时目录（`/tmp` 下），模型读完即弃，由操作系统按临时目录策略回收；如需稳定留存请用 `--outdir` 或 `--debug` 指定可见目录。

### 常见坑：依赖装好了却提示找不到

脚本每次启动都会先在 stderr 自报家门，打印它正在用哪个解释器：

```Plain Text
[video-reader] 解释器自检 (排查'装了却用不了'看这里):
  - python   : /usr/bin/python3
  - version  : 3.13.5
  - user-site: /path/to/python3.13/site-packages
```

> **症状：**明明刚用 `pip` 装过 `opencv`，运行时仍报找不到包。
> 
> **原因：**Mac 上常同时装了系统 `/usr/bin/python3`、Homebrew 和 pyenv 等多个解释器，而 `pip --user` 按 Python 版本分目录存包：装在解释器 A 里，脚本运行落到解释器 B，就会报错。
> 
> **排查与解法：**对照启动日志第一行的 `python` 路径，改用装过依赖的那个解释器绝对路径运行，或者建独立虚拟环境 `python3.x -m venv .venv` 锁死运行环境。

依赖装不上或找不到时，报错信息会直接贴出当前解释器路径和搜索目录，照着复制运行即可，不用再自己手敲排查命令。

## 设计上的几个取舍

- **静止段直接跳过：**静止帧不会卡顿，对查交互问题没帮助，还白占上下文；直接由代码剔除，模型只看有变化的画面。
- **时间戳不写进画面：**把时间戳写进文件名和 JSON，模型读文字几乎不出错，比在图片上打字认字符靠谱得多。
- **喂前先压缩尺寸：**模型视觉端本就会下采样切片，传超高清纯属浪费；默认压到宽 900、JPEG 质量 70，字迹清楚又省 token。
- **抗翻拍晃动：**靠先缩小、高斯模糊再分块算均值差，吸收拿手机翻拍带进来的反光与轻微手抖，但手指微动这类细节仍以真机录屏为准。
- **不强制要求屏幕录制小白点：**很多反馈视频压根没开录制手势提示，方案按「有小白点顺便参考，没有也能定位」设计。
- **脚本只算时间线不做业务判断：**脚本本身不懂卡顿或弹窗，只负责提帧与标秒数，具体定位全由大模型看图推理，方便跨场景复用。
