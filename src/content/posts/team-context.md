**是什么**：放在团队 Git 仓库里的工具加纯文本数据底座，同时生成给人用的 **HTML 交互网站**和给 AI 用的代码背景与红线（另支持导出文档兜底）。
**解决什么问题**：把散落在各平台、代码库和老员工脑子里的常识攒到一处，省去反复问人和翻旧文档，也用统一工程边界管住 AI 写的大量代码。
**形态与携带**：单仓按目录物理隔离。通用工具与模板已开源在 [GitHub team-context](https://github.com/Job-Yang/team-context)；拉入新公司内网后第一步先解除个人远端（`git remote remove origin`），团队真实数据锁在内网仓库里绝不外传。

# 团队资产与现有痛点

一名研发人员日常工作中 **85% 到 90% 的时间和决策**，实际只围绕 7 类团队资产展开；但这些资产常年散落在公司十几个平台和口头经验里，新人靠边问边踩坑才能凑齐，老员工切换业务一样头疼。

| 资产类别 | 具体包含哪些东西 | 平时散落在哪里 | 缺失或过时后的后果 |
|-|-|-|-|
| 研发环境与平台入口 | 拉代码、编译、真机调试、内测发包、CI/CD、发布、远程配置、AB 实验、Crash 与性能监控、日志检索、需求看板、权限申请 | 旧入职文档、收藏夹、群置顶消息 | 配环境卡半天；开实验、改配置、查报错到处求人给链接 |
| 代码架构与模块关系 | 跨端/客户端/服务端仓库清单、核心模块调用关系、各业务入口代码、近三个月常改热区与高频回滚模块 | 几年前画死的架构图、数十万行源码 | 只敢盯自己改的那几行，看不懂跨仓库上下游，改完连带报错 |
| 业务全景与主流程 | 团队做什么业务、核心页面功能、一条用户请求从端到服务端的完整流转、核心需求文档链接 | 各产品群、长篇 PRD、口头交接 | 新人只见局部功能，不清楚自己改的模块在整条链路里担什么责任 |
| 数据资产、埋点与评测 | 核心业务指标、关键技术指标、常用数据看板、核心数仓或业务表、埋点定义、AI 场景评测标准与坏例归因方法 | BI 平台、埋点后台、各处表格、周报 | 指标算错表、埋点漏报、线上效果波动说不清归端侧、链路还是模型 |
| 工程标准与 AI 写代码红线 | 命名与目录规范、必须复用的基础组件、禁止跨层调用的边界、合规安全底线、单测与回归验收要求 | 老员工脑子里、零散的 Review 评论 | 不同的人用不同的 AI 工具生成大量代码，风格散乱且频频破坏原有边界 |
| 避坑指南与历史决定 | 看着冗余却不能删的兼容和合规代码、当年为什么这么做取舍、线上反复踩过的大坑与故障复盘 | 沉底的故障文档、老员工的嘴里 | 新人和 AI 以为代码多余顺手删掉，直接触发历史线上故障 |
| 找人地图与工作分工 | 某个代码目录、某个报错、某张看板、某项平台权限出问题第一找谁，以及跨职能接口人（仅记工作分工，不记个人评价） | 滞后的组织架构图、群聊里乱问一圈 | 出故障先花二十分钟打听找谁，信息在多人转述中失真 |

AI 编程普及后还多出一个硬痛点：组里每人用的模型和工作流都不同，AI 动辄生成几千上万行代码，人工评审看不过来。缺少统一的机器可读红线，AI 写得越快越容易把工程改乱。

# 方案定位与区别

Team Context 是一套 **轻量工具加纯文本数据底座**，它区别于静态新人文档，也不打算替代公司级重型研发平台。

| 对比维度 | 传统团队文档（飞书/语雀） | 知识库全量搜索（RAG） | 单仓库 `AGENTS.md` | 公司重型研发门户 | **Team Context（本方案）** |
|-|-|-|-|-|-|
| 解决的核心问题 | 人写给人看的静态阅读 | 从海量文档里搜关键词 | 管住这一个代码仓的语法 | 公司级统一平台基建 | 团队级人机共用工作台 |
| 跨仓库与跨平台能力 | 靠人工粘贴链接，极易失效 | 只搜文本，无法打通代码关系 | 差，只管得了当前仓库 | 强，但研发改造成本高 | 强，一站串起多仓、看板与平台 |
| 人看起来方不方便 | 篇幅长、翻找慢、入口散 | 问答碎片化，看不到全局 | 不适合人浏览全景 | 好，但按公司通用模板来 | 极好，**可交互网页**一站直达 |
| 给 AI 用的效果 | 过时废话多，容易带偏 AI | 把草稿和旧方案全搜出来误导 | 好，但缺业务指标与避坑背景 | 一般不直接面向编码助手 | 极好，按任务喂准且统一红线 |
| 防过期与维护成本 | 写完即旧，全靠人自觉改 | 脏数据越攒越多 | 随代码提交一起改，维护较轻 | 需要专职平台团队维护 | 自动脚本重算，踩坑顺手补 |

- **定位边界**：只存精简结论、代码关系图、规范红线和直达链接，**不搬运长文档原文**。
- **反开倒车**：几千字的需求和复盘仍留原平台，本方案主入口是可交互网站与 AI 规则，静态文档仅作导出兜底。

# 核心原理与运作方式

这套东西能做到既省力、又能真正防踩坑，靠的是四条很朴素的底层设计：

1. **一份底层数据，服务两套消费端**：底层全部存成结构化纯文本。给人看的出口直接编成一个本地或内网可打开的 HTML 交互网站，把各种平台链接、代码关系图和经验摆在一块；给 AI 看的出口则只抽取简短背景和写代码红线，按当前干的活精准投喂。人与机器各取所需，互不拖累。
2. **先抓事实，再整理和确认**：靠人肉翻几十万行代码写文档肯定烂尾，全交给 AI 自由总结又爱胡编。做法是先跑几条只读脚本扫出真实的代码调用关系、最近 90 天改得最勤的文件、常出回滚的模块和活跃作者，再把团队现有文档喂给公司允许用的 AI，让它把信息拆成标准化草稿放进 `inbox/` 待审区。人只需要在写需求、调试或问同事时顺手核对、补全真实路径或链接，确认无误再放进正式区。
3. **用工程限制管住 AI**：不管是谁、用哪款 AI 编程助手，只要工具读了团队统一同步出去的规则和代码红线，就知道哪些底层组件不能绕开、哪些历史逻辑不能乱删、改完必须跑哪些检查。这样等于把原来靠人肉 Review 扛着的把关压力，提前移到了 AI 动手写代码之前。
4. **工具通用带得走，数据隔离留在公司**：所有采集脚本、网页生成器和安全检查脚本完全不绑死哪家公司，放在自己的 GitHub 仓库里走到哪都能用。每去一个新团队，自己摸索平台、梳理代码、对齐产品的过程，顺手就把这套数据攒了起来。先跑通让自己和项目立刻受益，做实了再分享给全组一起用，拿出能点开看的真东西比空谈框架更有说服力。

# 整体结构与仓库设计

从仓库落地上看，前期没必要拆成好几个库增加心智负担，用**单仓库内按目录物理隔离**最轻便：外层是人人可带走的通用工具与文档，内层是锁在公司内网的真实团队数据。

```text
team-context/                      # 单个工作区：外层工具可带走，data/ 仅留内网
├── README.md                      # 极简操作手册：4 条核心命令与进新公司防误推指引
├── AGENTS.md                      # AI 执行手册：冷启动 5 步与草稿确认规范（AI 进仓先读）
├── CLAUDE.md / SKILL.md           # 兼容 Claude Code 与 Agent Skills 生态的标准入口
├── docs/                          # 给人看的设计方案文档与结构图（可迁往个人网站）
├── scripts/                       # 零依赖通用 Python 工具脚本（仅用标准库 + 原生 git）
│   ├── tc_common.py               # 元数据解析、过期天数计算与路径安全检查
│   ├── init_team.py               # 一键初始化团队 data/ 与 data/inbox/ 草稿区
│   ├── scan_repo.py               # 自动分析代码结构、热改文件、回滚提交与目录维护者
│   ├── build_portal.py            # 编译单文件可交互 HTML 团队网站（附带导出 MD 兜底）
│   ├── sync_ai_rules.py           # 生成 AGENTS.md / CLAUDE.md / Cursor 规则与任务切片
│   └── check_safety.py            # 远端防漏、密钥/隐私/主观评价拦截与过期提醒
├── templates/                     # init_team.py 初始化时复制的 7 类标准空白模板
├── examples/sample-team/          # 虚构团队完整样例，拉库后零配置可直接体验网页
├── tests/run_selftest.sh          # 端到端自动化自测脚本
└── data/                          # 【已被 .gitignore 忽略，仅存公司内网绝不推公网】
    ├── inbox/                     # 待确认草稿区（脚本扫描与旧文档拆解产物暂存）
    ├── history/                   # 历史决议与事故复盘归档
    ├── platforms.json             # 研发环境与各类日常平台的一站式直达入口配置
    ├── code-graph.json            # 自动计算加上人工标注的代码关系图数据
    ├── business.md                # 团队业务全景与核心请求流转
    ├── metrics.md                 # 核心业务/技术指标、埋点与评测规则
    ├── standards.md               # 团队编码规范与 AI 写代码硬红线
    ├── pitfalls.md                # 避坑指南与重要历史决定
    └── owners.md                  # 模块负责人与跨职能找人地图
```

这里特意区分了三份文字材料各自的读者，避免混为一谈导致“人嫌啰嗦、AI 看不懂”：

- **给人看的方案文档**（比如本篇及未来放进个人博客的文章）：把来龙去脉、为什么做、收益和边界讲透，给未来的自己、老板或合作同事看。
- **给 AI 看的仓库入口**（根目录 `AGENTS.md`、`CLAUDE.md`、`SKILL.md` 与极简 `README.md`）：不写长篇背景，只写清目录约定、冷启动 5 步动作与严禁覆盖草稿的红线。任何新公司的 AI 助手进仓读一眼，立刻知道怎么扫库、怎么拆解旧文档并写入 `data/inbox/`。
- **团队的真实资产**（`data/` 目录）：采用统一小结构保存，既能被脚本秒级编进网页，也能被 AI 按需读取。

# 两大使用入口

同一份纯文本数据同时驱动两个使用端：人通过**可交互网页**一站看完所有平台与代码关系，AI 通过规则与按需背景管住代码质量。

## 给人用：一站式可交互 HTML 团队网站

本地一条命令编译打开，有条件时可直接挂上内网服务器当团队主页，告别同时开七八个公司平台来回切标签页；另保留一键导出汇总 Markdown 文档作兜底。

| 网站核心视图 | 它长什么样、能点什么 | 解决的真实日常麻烦 |
|-|-|-|
| 一站式平台导航墙 | 把拉库构建、CI/CD、发布、Crash 监控、远程配置、AB 实验、需求看板和权限申请做成卡片入口，附常用命令和注意事项 | 再也不用满世界找链接或翻群置顶，一个首页搞定 90% 的平台跳转 |
| 类 Obsidian 可交互代码地图 | 把各端仓库、核心模块与关键文件的依赖和调用画成可拖拽缩放的关系网，支持按业务流过滤，点击节点直接看说明或跳转到代码库位置 | 新人看全景、老人查跨端影响面一目了然，告别两年前就过时的静态架构图 |
| 业务与数据指标墙 | 按业务线列出核心页面流程、技术/业务指标定义、对应看板链接、数仓主表以及 AI Badcase 排查顺位 | 对数据、查异常时不必再到处问指标口头定义或找表名 |
| 避坑卡片与历史决定 | 支持按模块和关键词搜索“为什么不能删”、“当年为何这样设计”、“曾经怎么挂过” | 接手陌生模块动手改代码前花两分钟搜一下，少踩前人踩过的坑 |
| 找人地图与保鲜提示 | 按模块和平台列出当前接口人与主要提交者；所有超出核对日期或代码文件已挪走的条目自动标黄提醒 | 找人一眼定位，也能清楚看到哪块信息已经有点旧、需要顺便核对 |

## 给 AI 用：按需背景与工程红线

给 AI 看的部分刻意不做全量塞入，而是分“日常干活背景”和“通用工程红线”两层同步给组内常用的 AI 编程工具：

- **按任务喂准上下文**：写端侧页面、查埋点漏报、或者做跨端联调时，只把当前任务用到的业务流程、代码关系和对应避坑记录带进对话，省掉大量无关文字对大模型注意力的干扰。
- **全组同步代码红线**：通过 `sync_ai_rules.py` 将 `standards.md` 和高危避坑提炼成标准的 `AGENTS.md`、`CLAUDE.md` 或编辑器规则文件，同步到各业务代码仓。无论团队成员用什么模型或 IDE，AI 下手写代码前都会先受到同一套架构边界、组件复用规范和安全底线的约束。

# 资产吸收、更新与安全

一套团队工作台能不能用过半年，不看第一天搭得多漂亮，而看旧资料好不好收进来、新变化好不好顺手更进去，以及数据安不安全。

![图 2：Team Context 运转与更新循环](/assets/content/team-context/warehouse.webp)

读图提示：整套机制靠“自动扫描重算 + 踩坑顺手补录 + 草稿确认”循环保鲜，尽量不靠人苦写文档。

- **旧文档批量吸收**：进组后把现有新人指南、架构介绍和事故复盘交给获批内网 AI，按 7 类资产拆解去重并保留原链接，生成初版草稿进 `inbox/`；人结合跑环境和改代码核对一遍后转正，死文档就变成了活入口。
- **日常增量更新**：不同资产走各自最省力的通道，全部留在内网 Git 仓的 `data/` 目录下，自带版本历史和评审记录。

| 资产类型 | 以后怎么保持更新 | 改完数据往哪存 | 怎么同时生效给人与 AI |
|-|-|-|-|
| 代码关系图与高频作者 | 脚本按周或按需重新扫代码库与 Git 提交历史，自动刷新热区、依赖关系和主要维护者 | 覆盖更新 `data/code-graph.json` | 网页交互图谱立刻更新，AI 查模块归属同步刷新 |
| 平台入口、看板与文档链接 | 检查脚本定期核对更新日期与复核周期并在网页标黄提醒超期项；平台迁址时只需修改一行 JSON 配置 | `data/platforms.json` 与 `data/metrics.md` | 网站重编立刻换上新入口，导出文档兜底同步更新 |
| 新的避坑经验与历史决定 | **人不用专门写文档**：踩完坑或处理完事故后，把事情经过或复盘链接直接丢给 AI，AI 按固定小模板生成 5 到 10 行草稿放进待审区，人看一眼确认合入 | 先落 `data/inbox/`，确认后并入 `data/pitfalls.md` | 网页立即多出一条可搜索避坑卡片；高危约束同步提示更新进 AI 规则 |
| 团队编码规范与工程红线 | 在关键代码评审发现 AI 反复犯同一类错时，顺手往红线清单补一条“禁做某事 + 正反例子” | `data/standards.md`（随仓审核） | 跑一次同步脚本直接推送到各个代码仓的 AI 规则文件 |

<callout emoji="🔒">
**五类内容严禁入库**：任何账号密码、密钥与 Token、真实用户隐私样例、未脱敏的业务/医疗/金融明细数据、对同事工作表现或性格的主观评价，绝对不能放进 `data/`。
**双保险自动拦截**：`check_safety.py` 严格按零联网运行，自动拦住私钥、API Token、明文密码、手机号、员工主观评价以及向个人 GitHub 误提交 `data/`；同时检查更新日期与复核周期并标黄提醒超期项。整个 `data/` 目录只留在公司内网并只对接获批内网 AI，绝不外发公网。
</callout>

# 附录：Git 仓库最小说明模板与代码扫库命令

为了让外部带走的工具仓库做到“任何公司的 AI 进门就会用”，根目录 `README.md` 保持极度简洁，只交代目录分工与四条核心动作即可：

```markdown
# Team Context

面向研发团队与 AI 协同的通用工作台工具包（仓库地址：https://github.com/Job-Yang/team-context）。
工具源码与团队真实数据物理隔离：
- `scripts/`：零第三方依赖通用脚本（可跨公司复用）
- `data/`：当前团队的真实资产目录（默认被 `.gitignore` 忽略，仅存公司内网）

日常动作：
1. 进新公司第一步防误推：`git remote remove origin`
2. 零配置先看样例网页：`python3 scripts/build_portal.py --data examples/sample-team --out /tmp/sample-portal.html`
3. 初始化当前团队目录：`python3 scripts/init_team.py --data data --team-name "我的新团队"`
4. 只读扫描业务代码仓：`python3 scripts/scan_repo.py --repo <目标代码仓路径> --out data/inbox/scan`
5. 编译可交互网页与文档：`python3 scripts/build_portal.py --data data --out dist/index.html --export-md dist/team-handbook.md`
6. 同步 AI 红线到业务仓：`python3 scripts/sync_ai_rules.py --data data --mode rules --format agents --target <业务代码仓>/AGENTS.md`
7. 按任务抽取精选背景：`python3 scripts/sync_ai_rules.py --data data --mode context --task debug`
8. 安全拦截与过期检查：`python3 scripts/check_safety.py --data data`
```

代码自动扫库不依赖复杂环境，依靠以下几条只读 Git 原生命令即可提取最核心的代码活力、隐性关联与故障高发区：

```bash
# 1. 近 90 天修改最频繁的 Top 30 文件（一眼看清团队当前主战场）
git log --since="90 days ago" --name-only --pretty=format: \
  | grep -v '^$' | sort | uniq -c | sort -nr | head -n 30

# 2. 近 6 个月回滚与紧急修复提交（标记出最脆弱的高危模块）
git log --since="180 days ago" --oneline --grep="revert\|hotfix\|fix:" -n 50

# 3. 各核心目录下近 90 天高频提交人（生成不依赖过时架构图的找人映射）
git shortlog -sn --since="90 days ago" -- src/ Sources/
```
