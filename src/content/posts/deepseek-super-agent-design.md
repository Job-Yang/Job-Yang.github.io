> 原文：https://x.com/DeepSeekHarness/status/2116857257245987236

**Super-agent 值得借鉴的是把多项工作的协调交给系统，让人少花时间管理会话和搬运背景。** 写代码、显示状态或续接一轮对话，本身都不足以证明它比现有 Agent 更有价值。是否需要这套设计，要看现有工作流程还留下多少人工管理负担。

下文先解释原文的主张和证据，再按配套原型说明如何实现。原文讨论架构思路；原型只实现其中一部分；本文对应用接入的建议另行标明。

# 多任务先卡在人的注意力上

DeepSeek 原文提出一个判断：AI 越能独立完成单项工作，人就越可能把时间花在多项工作的协调上。同时修问题、做研究、处理评审时，人仍要记住每个会话的背景，判断新反馈该交给谁，并找出哪项工作需要自己决定。

| 人仍要处理什么 | 交给系统后，希望少做什么 |
|-|-|
| 群里提出修复，PR 里补充意见，背景分散在两处 | 自动把反馈送回原任务，减少重新交代背景 |
| 多项工作同时进行，要逐个会话查看进度 | 统一呈现需要回答的问题和待审阅结果 |
| 一轮执行结束或进程中断，仍要确认整项工作是否完成 | 保留工作记录，核对现场后继续，减少手工找回进度 |

这说明了架构要解决的问题，但还没有证明每个团队都遇到了它。只有当这些管理动作已成为实际负担，额外的任务协调系统才值得考虑。[原文第 1 节](https://x.com/DeepSeekHarness/status/2116857257245987236)

# 现有 Agent 够用时就直接复用

**比较对象应是已有工作流程，而不能只比较功能名称。** “能处理 PR”“能展示等待”“能跨渠道接续”可以由不同产品实现；关键是同一项工作从请求到交付，还需要人手动接回多少次。

已有能力确实与本文重合：Codex 的 GitHub 集成支持 PR 评审；Slack 集成可将仓库工作交给 Codex Cloud，在环境、权限和运行账号满足条件时，同一线程的相关请求可以续接编码任务。[GitHub 官方文档](https://developers.openai.com/codex/integrations/github)；[Slack 官方文档](https://developers.openai.com/codex/integrations/slack)

| 实际情况 | 本文的建议 |
|-|-|
| 单项工作背景集中，用户能够轻松跟进 | 直接使用现有 Agent；额外协调层的收益可能有限 |
| 多项工作持续进行，反馈分散，人频繁找会话、搬背景或追进度 | 先检查现有工具的任务关联、事件接入和续接能力，只补实际缺口 |
| 已有工具已覆盖请求、执行、评审、续接和恢复 | 直接复用完整流程，无须为了采用 Super-agent 再建同一层 |

因此，不能把“Trae／Codex 做不到”当成这篇文章的前提。下文解释的是一种可借鉴的架构方法；它是否带来新增价值，要由具体工作流程的对照决定。

# 两层分工兼顾协调与并行

假设确实需要系统接管多项工作的协调，下一步才是选择架构。原文讨论了两种直接做法：把所有事件交给一个会话，或为每个事件新建一个会话。两种做法分别容易保留全局背景和提高并行度，也各有代价。

| 组织方式 | 得到什么 | 需要解决什么 |
|-|-|-|
| 所有工作进入一个会话 | 背景集中，容易知道任务之间的关系 | 执行容易互相等待，不同任务的细节混入同一上下文 |
| 每个事件独立开会话 | 可以并行处理 | 相关工作容易断开，人可能需要重新协调背景和回复 |
| 全局协调与任务执行分成两层 | 全局判断集中，具体任务独立并行 | 需要维护任务归属、反馈投递和执行记录，也增加运行成本 |

**Router（全局协调者）处理跨任务判断与对外交流，Worker（任务执行者）专注一项工作。** Session 保存模型历史与工具调用上下文。每个 Worker 有自己的 Session；它内部仍可使用子智能体完成复杂任务。

下面是原型的具体实现：Engine（运行引擎）用程序保存事件、检查授权并派工，Router 用模型提交判断；Source 接入事件，Store 保存记录，Panel 展示工作。Ticket 是一项获准的工单，Assignment 是一轮执行安排。

![这是DeepSeek Super-agent原型的架构流程图，对应文档中提及的各核心模块的协作逻辑。图中上层应用/Panel作为入口，可发起查询或人工操作触发Engine模块；Engine接收来自Source（飞书/GitHub事件接入）的触发信号，完成归属校验、授权等核心处理，一方面将持久化的事件与工作记录存入数据库Store，另一方面生成执行安排Assignment派发给对应的Worker任务执行单元；Router模块接收Engine传递的待研判事件，输出决策信息后由Engine完成并行派工，Worker A、Worker B各自持有独立Session处理对应工单，全链路实现了全局协调与任务执行分层的运行逻辑。](/assets/content/deepseek-super-agent-design/super-01.png)

| 层 | 具体负责什么 | 在示意任务中做什么 |
|-|-|-|
| 上层应用 / Panel | 展示工作、问题和结果，接收人工操作 | 显示“启动崩溃：等审阅”，提供查看 PR、回答和停止入口 |
| Engine | 保存事件与工单，处理订阅、授权、派工和状态 | 让群消息与 PR 评论落到同一个 Ticket |
| Router / 主 Session | 判断新任务、协调跨任务信息、组织对外回复 | 判断需要修复，决定接单，汇总结果 |
| Worker / 执行 Session | 持有独立上下文，调用工具完成一项工作 | 复现崩溃、修改代码、测试、处理 PR 意见 |

Super-agent 与常见 Agent Team 的区别，在原文中体现为职责：Router 协调多项相对独立的工作，每项工作的拆解留给 Worker。已有 Agent Team 也可以按这种方式组织。比较时需要看具体职责和运行规则。[原文第 2.1 节](https://x.com/DeepSeekHarness/status/2116857257245987236)

原型进一步用订阅关系把已有任务的反馈直接交给负责它的 Worker，减少每次都经 Router 重新判断。新任务才进入接单评估。后半部分会解释这些记录和投递规则。[原型架构](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/007-architecture.md)

# 实验验证了调度上的取舍

**原文实验支持这组调度设计在模拟负载下的效果，尚不能推出它优于 Trae／Codex。** 每次约 300 条消息，其中约 20 条是工作请求，其余是闲聊、追问、取消和 CI 结果。每种配置运行 5 次，编码由只消耗时间的工具模拟，测的是调度与协调。

| 设计 | 完成耗时 p50／p95（分钟） | 每轮缓存读取 token |
|-|-|-|
| Super-agent | 12.4／15.7 | 23.2M |
| Super-agent，不做反馈直通 | 12.6／15.5 | 31.8M |
| 单会话＋子智能体，中性提示词 | 20.4／29.5 | 6.1M |
| 单会话＋子智能体，优先委派提示词 | 13.8／29.0 | 10.8M |

p50／p95 是任务完成耗时的第 50／95 百分位数；token 是模型计量的文本单位，M 表示百万。对比优先委派基线，Super-agent 的 p95 从 29.0 分钟降至 15.7 分钟，缓存读取量从 10.8M 增至 23.2M，约 2.15 倍。

原文把单会话的长尾归因于委派不稳定：模型有时判断工作“小”，选择自己执行。两层分工将 Router 不执行具体工作的职责固定下来。反馈直通在这次负载中没有明显缩短耗时，但减少了 Router 决策和缓存读取量。

实验没有直接比较现成产品，没有验证真实代码质量，也没有测量人的管理时间。因此，它支持的是调度取舍；是否值得用于我们的工作，仍要同时考虑人工负担、token 开销和系统维护成本。[原文第 7 节](https://x.com/DeepSeekHarness/status/2116857257245987236)

# 先确认人能少做什么

**采用这套设计的理由，应落在可观察的人工工作上。** 可以沿“群里提出启动崩溃、AI 创建 PR、人在 PR 中要求补测试”这条流程，检查背景是否需要重讲、反馈是否需要手动转交，以及中断后是否需要人重新找回进度。PR 是修改与评审请求，CI 是自动构建和测试等检查。

| 需要比较的结果 | 怎样判断有实际收益 |
|-|-|
| 任务接续 | 同一反馈能回到原任务，用户减少找会话、转发和重讲背景 |
| 人的介入 | 需要人回答或审阅时，问题和证据足够清楚，减少逐个任务追问 |
| 恢复与成本 | 恢复前能核对已做动作，避免重复；收益足以覆盖 token、部署和维护开销 |

若现有工具已做到这些，就直接复用；若只缺一段事件接入或任务关联，就先补那一段。任务接得回来、问题交得清楚、进度找得回去，才是值得比较的结果。

# 原型实现可按需查阅

以下说明固定版本的原型如何接单、投递反馈和恢复工作，供需要理解实现的人查阅。实体和运行规则来自固定源码；应用如何展示任务，是本文结合这些规则提出的建议。

## 消息如何变成任务线索

**Source（来源）收事件，Trigger（事件）记单次发生，Thread（讨论）组织连续消息。** Channel（回复地址）规定结果发到哪里，Subscription（订阅）把讨论与工单连接起来。

![这是一张对应消息转化为任务线索流程的实体关系示意图，图中以带说明的紫色模块依次标注六大核心概念：Source·来源示例为监听一个飞书群，可保留读取位置与账号；它“产生”Trigger·单次事件，对应一条报错消息，留存ID、发送人、时间；Trigger“归入”Thread·连续讨论，示例为话题A、PR#42，按时间组织事件；Thread被持有后关联到Subscription·订阅，后者用于连接Ticket与Thread，将后续事件投递到原工单；Thread还关联Channel·回复地址，示例为群话题回复、PR评论，指明结果发送位置，最终交付到Ticket·获准工作，对应修复启动崩溃这类任务，由它关联对应订阅关系。图例标注了图中箭头代表一对多、可选的关联规则。](/assets/content/deepseek-super-agent-design/super-02.png)

| 对象 | 是什么 | 同一个例子 |
|-|-|-|
| Source，来源 | 事件流；一种接入实现可配置多个实例，各自保存读取位置和账号身份 | 飞书接入实现，配置为监听研发群；GitHub 是另一种实现 |
| Trigger，事件 | 一条不可变的发生记录，包含 ID 与来源元数据 | “应用启动就崩了”这条消息；之后的 PR 评论是另一条 Trigger |
| Thread，讨论 | Source 定义的一组按时间排列的事件 | 飞书话题 A 与 PR #42 是两个 Thread |
| Channel，回复地址 | Thread 的写入端；描述如何向外发送结果 | 向话题 A 回复，或向 PR #42 写评论 |
| Subscription，订阅 | 一个 Ticket 与一个 Thread 的连接关系 | 修复工单同时订阅话题 A 和 PR #42 |
| Correlation，关联 | 多个 Thread 共享一个 Trigger 时的上下文关系 | 同一个外部事件归入两个讨论，系统据此查相关背景 |

**Thread 与 Ticket 是多对多。** 一项修复可订阅群话题和 PR；同一群话题也可能产生几项独立工作。相关消息会投递到仍在工作的订阅工单，工单是否立即执行还取决于容量、受阻状态等条件。Correlation 只帮助查背景，不投递任务。[领域模型](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/001-domain.md)

因此，任务详情可以列出关联群话题、问题单（Issue）和 PR，用户沿链接查看背景，不必复制整段消息。

## 接单与执行各有自己的记录

**Ticket 保存“获准做什么”，Assignment 保存“这一轮由谁执行”。** Executor（执行器）是运行派工的接口；原型通过它准备目录、启动 Worker 并传递消息。工作身份留在工单中，模型上下文留在 Session 中。

![这张示意图清晰梳理了DeepSeek Super-agent原型实现里的工单与派工关联逻辑：左侧纵向依次关联Ticket工单、Assignment一轮派工、Report结构化报告三类核心对象，Ticket工单示例为修复启动崩溃，标注重试时仍归属同一项工作，遵循先占后验规则；右侧对应展示三类关联对象：Mandate授权依据为工单的引用来源，Input执行输入记录请求与反馈状态，Session执行上下文留存模型调用历史。图中还通过不同连线标识对象间一多、可选的关联关系。](/assets/content/deepseek-super-agent-design/super-03.png)

| 对象 | 是什么 | 同一个例子 |
|-|-|-|
| Policy，策略 | 有版本的接单规则：谁可发起什么工作，哪些主动任务可接 | 允许指定成员请求修复，主动发现问题先观察 |
| Eval，评估 | 对一批事件作判断；准入检查谁能发起工作，模型研判再判断该做什么 | 判断报错是否要求新工作，是否已有工单处理 |
| Decision，决定 | Eval 结果：accept 接单、stop 停止、ignore 忽略、unavailable 未完成评估 | 修复请求获接单；普通闲聊被忽略 |
| Mandate，授权依据 | 接单时固定的范围、策略版本、来源身份与依据强度 | 修复请求是人明确提出的；不能因此扩大到重写登录模块 |
| Ticket，工单 | 一项获准的工作，持有授权、输入、交付地址和执行记录 | “修复启动崩溃”这项工作 |
| Assignment，派工 | 工单与一个 Executor 实例之间的一轮执行绑定 | 第一轮修复；重试后产生第二轮派工 |
| Input，执行输入 | 实际交给工单的上下文，并记录投递与读取情况 | 原请求、CI 结果、补测试的评论、策略变化通知 |
| Report，报告 | 派工返回的结构化进展、等待、就绪、受阻或失败 | “PR 已准备好，等待审阅” |
| Executor，执行器 | 运行 Assignment 的接口，连接工单规则与具体执行环境 | 准备目录、启动 Worker、投递 Input、回报 Report |
| Session，上下文 | 模型的消息历史和工具调用容器 | 原型中的 worker-<ticket id> 执行 Session |

接单时，Engine **把 Ticket、Mandate、首轮 Assignment 和订阅一起写入**，避免只建工单却漏掉派工。Mandate 的依据强度分为“人明确提出”与“系统按规则推断”；后者是否执行，由当前策略决定。

重试只换一轮 Assignment。这个原型继续使用原来的 Ticket、Session、目录、分支和 PR。模型停了一轮、命令失败或会话空闲，都不自动等于工作结束。[执行规则](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/003-execution.md)

## 一项工作怎样跨渠道继续

**这个原型按订阅关系把反馈送回原任务。** 用户在群里提出修复，在 PR 中补充意见，系统据此找到原 Ticket。图中沿同一项修复说明请求、反馈和结果如何流转。

![这是一张跨渠道工作流转时序图，直观呈现单条修复需求从发起闭环落地的全流程。图中沿纵向排布“人”、Source、Engine、Router、Worker五大角色模块：上半部分展示初始修复请求经研判通过后生成工单、派工执行并同步关联PR的流程；下半部分展示跨渠道接续环节，PR新增的补充测试评论生成新Trigger后，依托订阅直通Input，依次完成进展结构化上报、结果推送，最终向用户返回带验证证据的执行结果，清晰对应文本提及的两处核心交接规则。](/assets/content/deepseek-super-agent-design/super-04.png)

读图时关注两个交接：新请求经过准入与研判后创建工作；PR 已关联工单后，新的人类评论先交原 Worker。Input（执行输入）保存交给它的消息，Report（结构化报告）保存它回报的进展与结果。最后由发送适配器写到 Channel。

| 情况 | 系统怎样处理 |
|-|-|
| 新请求，尚无工单负责 | 进入 Eval；准入通过后，由主 Session 接新单，或将消息明确关联到已有工单 |
| 已订阅讨论中，人要求补测试 | 作为 Input 送到原工单，Worker 在原范围内继续 |
| 同一评论要求另一项独立功能 | Worker 退回；没有其他工单继续负责后，再交 Eval 判断 |
| CI 或机器人发来结果 | 活跃订阅工单收到背景；也可独立进入准入评估，但不能唤醒已结束工单 |
| 订阅另一个 Issue 只为查背景 | 能收到信息，但不能因此扩大授权，也不能唤醒已结束工单 |

“关联已有工单”是绑定消息与讨论的操作，不是再接一份新单。**只要原执行者还负责这条人类反馈，Router 就不能同时把它接成另一项工作。** 退回或释放后，才重新评估；授权范围始终由 Mandate 保留。[授权与续接](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/002-authorization.md)

长命令先返回 Started（已启动），后台完成后再通知执行者。原型的 shell，即终端命令，前台等待上限为 5 秒；新输入在下一模型步骤处理。仍在运行的后台任务保留执行名额，不能把“这一轮对话结束”误记为“任务空闲”。

主动任务也走接单体系：按规则发现候选、评估后执行。默认 observe（观察）只记“本来会接什么”；auto（自动）才执行合规候选；off（关闭主动接单）不产生推断候选。人明确提出的请求在这三种模式下仍可处理。

## 任务状态用于提示下一步动作

**状态展示是工作台的常规要求。** 它的作用是让人知道下一步该回答、审阅还是等待，不能单独作为 Super-agent 的优势。原文第 8.2 节把任务呈现与交互方式列为开放问题；下面说明的是配套原型的一种实现。[原文第 8.2 节](https://x.com/DeepSeekHarness/status/2116857257245987236)

原型把“模型空闲”和“任务完成”分开：Ticket 生命周期主要是 open（未结束）与 ended（已结束）。open 内仍可能排队、等待、受阻或待审阅；应用阶段从记录派生，不是另一套独立状态。

![这张图是DeepSeek Super-agent的任务状态流转流程图，展示了任务的不同阶段及跳转逻辑。流程从代表起点的“执行中”（Ticket: open）阶段开始，其状态满足不同条件时会发生跳转：当报告ready且存在PR时，会进入“等审阅”（Report: ready + PR）阶段；若PR关闭且工作完成，则跳转至终态“已结束”（Ticket: ended）。“执行中”还可能因“人停止”跳转至“人工停止”状态，同时存在“收到修改意见”“人追问且授权仍有效”等箭头标注的状态触发条件，图例也对各阶段的状态属性进行了说明，对应文档中任务状态用于提示下一步动作的相关内容。](/assets/content/deepseek-super-agent-design/super-05.png)

| 界面阶段 | 判断依据 | 人在这里做什么 |
|-|-|-|
| 输入未送达 | Input 投递失败 | 查看投递问题；重试或等待恢复 |
| 等回答 | Attention：一项结构化的待人工问题 | 回答具体问题 |
| 等审阅 | 最新 Report 为 ready（就绪）；PR 任务仍未结束 | 查看结果和证据，决定是否接受 |
| 受阻 / 失败 | Report 为 blocked / failed，尚无人续接 | 处理缺输入或失败原因，续接或重试 |
| 排队 | 没有派工或 Assignment 仍为 pending（待启动） | 看见正在等待执行容量 |
| 等后续事件 | Report 为 waiting（等待），或一轮派工已结束 | 等 CI、相关消息或后续要求 |
| 执行中 | 以上条件均不匹配；Worker 在工作或后台任务未完 | 查看进展，必要时补充要求 |

上表针对 open 工单，**从上往下取第一个匹配阶段**：同时输入投递失败、又报告就绪，应显示输入未送达。已结束工单另行展示。Assignment 的 pending → running → ended 只是派工从待启动到运行、再到结束，不决定 Ticket 是否结束。

有 PR 的 ready 通常表示等审阅。完成条件优先看工单自己创建的 PR 是否都关闭；没有自建 PR，才看它跟踪的 PR 是否都关闭，并等待未完续接工作。ready 且没有关联 PR 可以直接结束，有没有群讨论并不决定完成。

> PR 关闭可能对应合并，也可能对应未合并关闭。界面还应展示结束结果；图中的“已结束”不能一律理解为修改已合入或任务成功。

正常结束保留订阅和授权。人后来在原讨论追问，经当前策略重新校验授权后，可以续接同一 Ticket；机器人和 CI 不会唤醒已结束工单。**人工停止会撤回授权**，后续工作需要重新接单。

> Attention（待人工决定）是一项带明确问题的记录，例如“需要保留旧系统兼容吗？”它必须来自结构化字段。应用可以把问题和待审阅结果置顶，避免从日志措辞猜任务是不是在等人。

## 历史怎样找回，故障怎样恢复

**完整档案在窗口之外，窗口只放当前有用的线索。** 这使系统能跨会话继续查证，又不把所有任务的长日志都塞给 Router。

![这是一张用于阐释历史找回、故障恢复流程的数据流示意图，整体分为三个依次推进的核心阶段：01/当前线索、02/任务与原件、03/需要的上下文。流程从“PR评论卡片”起始，沿ID查任务跳转至“Ticket卡片”，再追溯源请求抵达“最初群聊请求”；同时Ticket卡片可按引用读取存储在窗口外的“完整历史/日志”，最终向当前模型窗口仅分页选取、加入相关片段。图中通过绿色箭头标识主要数据流向，紫色区块标记数据存储节点，清晰呈现了沿关联ID逐跳召回历史、精简纳入上下文的运行逻辑，和文档中Chain of Recall等召回机制的说明完全对应。](/assets/content/deepseek-super-agent-design/super-06.png)

| 机制 | 具体动作 | 对应用的意义 |
|-|-|-|
| Inline | 直接给模型摘要、对象 ID 和邻近信息 | 当前任务有足够线索，不必每次从零搜索 |
| Spill | 超长内容留在外部，窗口只保留读取引用 | 长日志和原件可追溯，避免撑满上下文 |
| Chain of Recall | 从当前对象沿关联 ID 逐跳读取 | 从 PR 评论找到 Ticket，再找最初群请求与历史报告 |

卡片是给模型看的对象摘要，带 ID、内容预览、总长度与读取引用。长文本可分页。应用可对应提供“查看原请求”“查看相关 PR”“查看执行证据”，沿关系打开原件。

恢复还需要保存**已经发生的动作**。图中三个部分有各自的生命周期：运行进程可以重启；Store 保留任务与待办；执行目录和外部 PR 保留工作现场。

![这是一张DeepSeek Super-agent故障恢复与历史回溯机制的流程图，直观呈现了各组件的关联逻辑。图中以不同底色区分组件类型：绿色框为运行进程与Executor，分别对应Runtime/引擎/会话、原Session/目录/分支；紫色框为数据库类的Store-SQLite，负责存储工单、输入、派工与待办；灰色框为外部系统，分别是独立检查存活与进度的外部Watchdog、存储已生成PR与评论结果的GitHub/飞书，橙色框为Effects/Outbox，负责取待办、投递、保存回执。图中箭头标注了各模块的交互规则，完全对应文档中“运行进程可重启、Store保留任务待办、外部系统留存工作现场”的故障恢复逻辑。](/assets/content/deepseek-super-agent-design/super-07.png)

| 部件 | 负责什么 | 崩溃后有什么用 |
|-|-|-|
| Runtime | 创建组件，管理启动和停止 | 启动时装配系统并恢复中断派工 |
| Store | 原型的 SQLite 持久记录 | 找回工单、输入、订阅、派工与回执 |
| Effects | 持久动作队列；事务提交后才执行 | 找回未完成的启动、投递和转发待办 |
| Outbox | 对外消息与发送回执 | 找出尚未发送的回复，保留已发送或丢弃记录 |
| Watchdog | 主系统外的独立检查循环 | 检查基础故障；文章还提出用模型判断是否停滞或偏离目标 |

例如 PR 已创建、进程在记回执前崩溃，恢复时须先查本地分支和 GitHub，确认 PR 是否存在。持久队列和投递去重支持恢复，但不能保证所有外部动作自动恰好发生一次。

文章进一步提出把 Agent Loop（模型决策与工具调用循环）放在云端，状态放数据库，执行环境留在本机，通过 daemon（常驻连接进程）连回系统。设备离线，依赖它的工作等重连。**配套原型仍在本地集中运行**，使用专用运行配置和 SQLite 数据库。

## 新部署需要适配哪些位置

**原型提供的是部署扩展边界，接入新工具仍需要适配。** 实体和规则可以复用，Source、Policy、Executor 与 Channel 的具体实现属于部署。若希望复用其他 Agent 执行工作，需要核对它的启动、消息投递、状态回报和恢复接口；本文没有验证 Trae／Codex 可直接替换原型执行器。

| 要迭代的能力 | 接入位置 | 一个具体用法 |
|-|-|-|
| 新的业务入口 | Source 的接入实现与配置实例 | 将表单提交、业务消息或定时条件翻译为 Trigger，定义 Thread 和回复地址 |
| 业务接单与主动规则 | Policy + 主 Session 研判 | 判断哪些请求应处理；先 observe 看候选，再放开主动执行 |
| 某领域的执行能力 | Executor + Worker 工具与技能 | 给工单准备环境，运行业务工具，返回 Input 已读情况和 Report |
| 新的交付渠道 | Source 的 Channel 实现 | 把结果发送到指定业务页面或讨论，并保存发送结果 |
| 工作台与人工决策 | 管理 API / Panel / 只读视图 | 展示工单、问题、关联讨论、证据；调用回答、停止、重试入口 |
| 业务过程与复核要求 | 团队提示词、Worker 技能、平台限制 | 定义结果格式和验证要求，重要动作由真实工具权限约束 |

Engine 是工单与状态的统一写入入口。应用通过 API（程序操作接口）接入，避免直接改数据库：receive 接收事件，bindThread 绑定讨论，stopTicket 停止工单，retryTicket 重试派工，report 上报结果。

这些是可复用的接口边界。现有原型仍有直接依赖 GitHub、飞书的设置、资源读取与发送逻辑；接入新平台时，需要一起核对这些适配位置。

> 本文对应用的建议是：以任务详情关联范围、来源、执行轮次、问题和结果，让用户少查会话。一段对话可以谈几项任务，一项任务可以关联几段对话；具体界面应由业务流程决定。

需要接入时，先让一条真实流程完成请求进入、正确归属、反馈续接和结果审阅，再决定是否扩充入口。若现有应用已覆盖这些步骤，直接复用更合适。
