> **先说结论**：让 Agent 在 iOS 工程里持续干活，需要把程序员原本靠自己完成的反馈接给它。目标和上下文决定往哪走，编译与运行结果决定下一步怎么改，记录和止损让长任务接得下去。iLoop 要组织的，就是这套工作循环。

这篇沿着直播 SDK 裁剪这个通用场景，回顾一套自闭环 Agent 的设计如何逐步形成：范围怎么定，反馈怎么接，什么时候能继续，什么时候必须停下来。具体产品、业务指标与运行现场不在这里展开。

更抽象的设计与持续交付思路，可以接着读[《iLoop 的设计思路》](/writing/iloop-设计思路/)。

## 背景：删代码之前，要知道哪些行为必须留下

直播 SDK 的包体积优化，难点在于删掉能力之后，保留的功能还能不能正常工作。一个模块看起来独立，运行时却可能被 category、依赖注入、反射或动态注册连接到其他模块。

“裁掉了”也有不同含义：

- **物理删除**：源文件确实移除了。
- **构建排除**：文件还在，但不再参与当前目标的构建。
- **上层降级**：功能入口被隐藏，底层实现可能还在。
- **保留接口**：调用方仍能编译，接口后的实现已经变了。

这几种方式的包体积收益和影响面都不同。文件少了多少，不能直接回答功能有没有被裁掉；编译过了，也不能直接回答保留链路是否完整。

每轮改动后，人通常还要编译、安装、启动、进入特定页面，再看日志、界面和崩溃信息。任务持续多轮时，这条检查链很容易变成瓶颈。

**反馈**是这篇的关键词。Agent 要接手的，不只是删除动作，还有动作之后的判断。

## 范围不清楚，先把上下文交叉起来

裁剪最早遇到的问题是：哪些能动，哪些必须保留？单看一份模块清单，往往答不准。

| 上下文来源 | 能提供什么 | 需要补的判断 |
| --- | --- | --- |
| SDK 源码 | 当前实现、依赖和入口 | 模块量大，需要逐步下钻 |
| 历史裁剪经验 | 已确认的删除范围与保留理由 | 旧结论是否仍适用 |
| 产品需求 | 需要哪些用户能力 | 需求还要映射到代码 |
| 裁剪原则 | 基础能力与兼容约束 | 原则不能直接当删除清单 |
| 相似工程的方案 | 可以参考的边界 | 不同工程的依赖不能照搬 |
| 维护者的经验 | 隐含约束和历史问题 | 口头经验需要记录、再验证 |

这些材料要交叉使用，再回源码核对。一个可执行的过程是：

1. 扫描相关组件，先整理模块与子模块清单。
2. 从需求、原则和历史经验里提取保留或删除的依据。
3. 给每个候选写出裁剪意见与理由。
4. 新上下文出现后，复核已有判断。
5. 把仍待确定的部分交给了解边界的人确认。

裁剪表到这时仍是一份经验判断。**待确定就是待确定**，不能因为表格填满了，就把它当成百分百正确的执行计划。

## 为什么选择 Agent，还要让它用脚本

规则明确的部分，脚本很有效。比如列出文件、整理依赖、按已确认规则生成清单。但模块级意见通常不足以直接决定每一处代码怎么改。

| 做法 | 适合承担的工作 | 主要限制 |
| --- | --- | --- |
| 人工处理 | 确认边界、解决高风险判断、验收 | 连续盯住每轮构建和修复，成本高 |
| 按规则写脚本 | 重复、确定、可批量验证的动作 | 规则不完整时容易误删 |
| Agent 配合工具 | 按反馈调整方案，处理局部差异 | 必须有可靠反馈与明确止损条件 |

所以让 Agent 按表逐项推进，同时把确定的重复动作交给脚本。发现编译错误后，它读依赖和报错，修当前问题；这一轮达到验收标准，再进入下一项。

这里也可以顺便理清三者的分工：

- **Agent**：根据目标和反馈，规划、执行、调整下一步。
- **Skill**：告诉它某类任务怎么处理。
- **MCP**：提供与外部工具交互的协议接口。

三者可以配合。把脚本、Skill 或 MCP 接上，并不自动意味着 Agent 已具备持续交付能力，后面还要解决“怎么知道做对了”。

## iOS Agent 最先要补的是反馈

前端开发常有一条容易接通的写代码、构建、浏览器查看链路。iOS 同样具备编译和调试工具，但这些能力需要进入 Agent 的工作循环，结果也要能被它理解。

<img src="/assets/content/iloop-origin-retrospective/feedback.webp" alt="工具已接通与反馈未接通的对照示意" width="1536" height="1024" loading="lazy" decoding="async" />

图里的前端与 iOS 是反馈接通情况的对照，不代表 iOS 缺少调试能力。问题在于 Agent 改完之后，能否取得足以判断结果的信号。

| 难点 | 为什么静态看代码不够 |
| --- | --- |
| Objective-C Runtime | category、动态注册、反射和依赖注入会影响运行时行为 |
| 工具链环境 | macOS、Xcode 与构建配置共同决定能不能编起来 |
| 构建目标 | workspace、scheme、依赖与签名可能让构建落到错误目标 |
| 设备与沙盒 | 运行结果需要从设备、日志、视图或崩溃报告里取得 |

命令退出成功，只证明命令执行结束。还要看构建的成功标志、产物和目标，才能确认这次构建确实满足要求。

XcodeBuildMCP 这类工具，可以把编译、安装、运行、截图接给 Agent。接通这条链之后，才有条件讨论自动修复和连续执行。

## Harness：目标在前，反馈在后

Harness Engineering 讨论的是模型之外的工作环境：怎样引导模型行动，又怎样让它看到偏差。

<img src="/assets/content/iloop-origin-retrospective/harness.webp" alt="前馈引导方向、反馈帮助持续纠正" width="1536" height="1024" loading="lazy" decoding="async" />

可以借控制论里的“调速器”理解这件事。模型负责判断和行动，周围的工具与规则负责提供方向、观测结果、约束继续执行的条件。

- **Guides，前馈**：动作之前提供目标、上下文、项目约定、历史经验和工具说明，提高第一次做对的概率。
- **Sensors，反馈**：动作之后返回编译、测试、日志、界面或崩溃信息，让它知道判断是否成立。

只给规则，Agent 不容易知道规则有没有生效；只给报错，又会缺少正确方向。两种输入需要配合。

人类程序员也是这样工作。我们写完要编译，运行后看日志，异常时打断点。没有人能稳定地一次写对，Agent 也需要同样的修正机会。

## 上下文要分层，还要能重新找到

一个聪明的新同事接手工程，也需要先了解这摊事。Agent 需要的上下文同样有层次。

<img src="/assets/content/iloop-origin-retrospective/context.webp" alt="越贴近项目的上下文，越需要明确提供" width="1536" height="1024" loading="lazy" decoding="async" />

| 上下文 | 怎么补给 Agent |
| --- | --- |
| 公开知识 | 使用模型已有知识，再核对关键判断 |
| 领域知识 | 提供对应框架与技术机制的资料 |
| 项目术语 | 解释词语在当前工程里具体指什么 |
| 代码上下文 | 提供源码、依赖和入口的检索方式 |
| 运行时上下文 | 用实际日志、视图和崩溃报告补足 |
| 业务上下文 | 说清保留能力、使用场景和兼容要求 |
| 历史经验 | 把临时方案、隐含约束和踩过的坑写下来 |

不需要每轮都粘贴全文。可以约定一个输入目录，把原始需求、裁剪原则、用例和历史资料集中放好，让 Agent 知道需要时到哪里取。

材料有变化，再读取和归纳；没有变化，就沿用已有摘要。原材料和给 Agent 用的归纳分开，既减少重复输入，也保留了判断的出处。

但上下文多，不等于上下文清楚。长任务更需要围绕当前目标取材料，把暂时无关的信息留在文件里。

## 分阶段，才知道什么时候算完成

裁剪任务不能从头到尾只用一个标准验收。恢复能力、解决编译、缩小体积和检查运行行为，各自要回答的问题不同。

| 阶段 | 当前目标 | 完成依据 |
| --- | --- | --- |
| 恢复基础能力 | 让需要保留的能力进入工程 | 构建目标与依赖成立 |
| 解决编译问题 | 修正接口、引用和链接问题 | 正确目标编译通过 |
| 按表裁剪 | 逐项执行已明确的范围 | 改动可追溯、可回退，构建仍通过 |
| 验证运行行为 | 确认保留链路没有被改坏 | 对应入口、行为与运行证据满足标准 |

前几个阶段可以围绕编译推进，但整个任务收口时，仍要回答运行起来是否正确。**编译成功不等于运行正确。**

阶段划分还有一个作用：让人能跟上 Agent 的进度。每轮只做一个清楚的小目标，理解与验收才能落到具体变化上。

### 先让编译反馈形成循环

构建系统输出的依赖关系，对人可能是一大堆文件，对 Agent 却可以是一份可检索的结构化材料。它能把报错与依赖连起来，判断缺的是引用、接口还是构建配置。

这一轮选好范围，做最小改动；编译不过，就读报错和依赖再修；通过之后，记录改了什么、为什么改、涉及哪些文件，然后才选下一轮。

### 把运行态接到同一条循环上

运行验证不用另起一套流程。编译过后，在同一轮里取得运行证据，再判断是否达到目标。

下面把同一轮工作的编译与运行分支分开列出。每个分支都写明下一步回到哪里。

### 编译回路

| 当前结果 | 下一步动作 | 回到哪里 |
| --- | --- | --- |
| 开始本轮 | 做最小范围改动，再编译 | 编译检查 |
| 编译失败 | 读取依赖与报错，修正当前改动 | 重新编译 |
| 编译通过 | 安装、启动并取得运行证据 | 运行检查 |

### 运行回路

| 当前结果 | 下一步动作 | 回到哪里 |
| --- | --- | --- |
| 行为符合目标 | 记录依据并验收 | 有下一项则继续，否则收口 |
| 行为不符合目标 | 分析偏差并修正改动 | 返回编译回路，再验证运行 |
| 被环境或输入卡住 | 留下证据，升级用户处理 | 条件具备后，重新确认本轮目标 |

回路需要止损条件。环境、签名、账号或缺输入挡住下一步时，要说明卡在哪，交回用户判断，不能靠不断重试掩盖没有进展。

## 运行验证留下的难题，也要如实讲

原稿的运行验证目标，是让 Agent 自动进入页面、取得证据、判断改动有没有影响保留能力。这条路没有完整跑到全自动。

iOS 的设备条件决定了这件事很难靠一套固定动作解决：

- **模拟器**：部分 SDK 能力不能在模拟器完整验证，要先确认当前链路是否受支持。
- **真机**：签名、账号、登录态、网络和应用状态可能形成需要人处理的卡口。
- **入口自动化**：找到静态入口之后，不一定能自动完成实际交互。

所以运行态验证需要人工兜底。必须区分“分析工具能产出候选”和“设备上已经验证正确”，不能把前一种结果写成后一种完成。

### 影响面分析可以帮回归聚焦

裁剪后，先把变化映射到模块、入口和测试用例，再决定哪些必须测、哪些抽样、哪些仍待确认。

| 需要回答的问题 | 可以使用的证据 | 结论边界 |
| --- | --- | --- |
| 哪些用例可能受影响 | 变更、依赖、用例描述 | 得到回归优先级，仍需验证 |
| 哪些入口可能残留 | 路由、UI、资源和动态注册 | 得到入口候选，不能代替实际交互 |
| 崩溃是否可能来自改动 | 堆栈、变更范围、复现条件 | 归因分级需要补反证 |
| 保留链路是否正常 | 设备上对应操作与运行证据 | 只覆盖实际验证过的范围 |

风险分层的目的，是把验证资源放到最相关的路径上。低风险也需要依据，不能让模型一句“应该没事”变成免测理由。

### 证据按要回答的问题来选

没有必要遇到每个问题都把截图、日志、UI 树全部跑一遍。

- 验字段和执行路径，优先看日志。
- 验控件存在与位置，优先看 UI 层级。
- 验最终画面，实际查看截图。
- 验崩溃，查看 crash report 与复现条件。
- 验构建，核对成功标志、目标和产物。

工具动作成功，只是拿到了材料。材料是否支持结论，还需要对照这一轮的目标。

## 长任务需要记录、记忆和止损

闭环接通后，跑久了还会遇到新问题：上下文塞满，重复犯错，会话中断之后不知道从哪接着做。

| 要补的能力 | 解决什么问题 | 具体做法 |
| --- | --- | --- |
| 文件与 Git | 中间状态放不进模型上下文 | 改动、依据和证据落盘；授权范围内保留可追溯版本 |
| 错题本 | 新会话不会自动记得上次的坑 | 记录现象、根因、解法，下次先检索 |
| 上下文管理 | 长会话中相关信息被挤掉 | 先归纳材料，只补当前最小证据缺口 |
| 任务清单 | 中断、早停或跨会话丢进度 | 保存目标、完成标准和待办 |
| 强制约束 | 提示词要求不一定被执行 | 将关键检查接到实际流程或工具里 |

错题本帮助的是下一轮的判断。把问题写进文件，不代表模型权重已经更新；还要能在需要时检索并使用。

记录也要尽量具体：这一轮改了什么，依据是什么，验证了哪些范围，什么仍未知。下一次恢复先核对这些信息与当前工程状态，再决定是否继续。

## 专项能力与通用循环分开

把任务方法整理成工具链时，可以分成两部分。

| 层次 | 放什么 | 随任务变化的部分 |
| --- | --- | --- |
| 通用循环 | 目标、上下文、工具调用、反馈、止损、记忆和验收 | 换任务仍需保留这些判断 |
| 专项能力 | 模块清单、裁剪索引、入口映射、用例分层 | 依业务与工程替换 |

专项工具可以整理模块和变更，扫描入口，解析用例，给出风险分层，生成探测计划，汇总影响面。通用循环负责决定本轮做什么、怎么验证、何时继续或交回用户。

过程产物也应分开保存：

- 输入材料：需求、原则、模块清单和测试用例。
- 分析结果：依赖、入口、影响面和风险判断。
- 运行证据：构建结果、日志、界面和崩溃报告。
- 任务记录：进度、判断依据、未解决问题和经验。

这些是继续工作与复核结论的依据。公开分享时，具体工程资料和运行现场还需要单独审核，不能直接把工作目录搬到文章里。

## 放手之前，先看任务是否具备条件

并非所有任务都适合交给 Agent 连续执行。原稿把这个判断整理成一组检查。

<img src="/assets/content/iloop-origin-retrospective/suitability.webp" alt="连续执行前需要核对目标、反馈、纠偏与记忆" width="1536" height="1024" loading="lazy" decoding="async" />

| 要核对什么 | 不满足时怎么办 |
| --- | --- |
| 总目标是否明确 | 先澄清要达到的状态 |
| 每轮和每阶段目标是否明确 | 拆成可验证的小目标 |
| 结果是否有判断标准 | 先定义完成依据 |
| 上下文是否清楚 | 补资料、约束和待确定项 |
| 反馈是否可靠 | 先接通能检验结果的工具 |
| 出错是否能纠偏 | 规定止损和升级条件 |
| 经验是否能复用 | 保存并检索已确认的教训 |
| 长期状态是否能恢复 | 落任务记录，恢复前核对 |

图中的检查描述的是执行条件。检查通过，也仍要遵守当前用户授权和验收范围，不能把它当作无限制自动执行的许可。

原稿还提到一个容易忽略的方向：上下文不只来自输入目录。录屏、请求数据、需求描述、崩溃材料，都可能提供静态源码里没有的信息。关键是把当前任务需要、且有权使用的材料接进来。

## iLoop：给 Agent 一个程序员式 Loop

iLoop 把前面这些判断组织成一种不绑定裁剪任务的工作循环：理解目标，取得上下文，执行改动，取得反馈，修正判断，再记录这一轮的结果。

客户端开发里有一个熟悉的类比。函数接收输入、返回结果；应用还需要持续接收交互和反馈，靠 RunLoop 组织后续工作。Agent 的单次回答也像一次函数调用，长任务则需要维持状态，并据反馈决定下一轮。

iLoop 这个名字，最初是 iOS 的 i 加上反馈闭环 Loop。它要让不同工程任务接入前馈与反馈系统，在上层继续补业务上下文和验证能力。修 bug、做需求、重构或排查运行问题，都可以使用同一种循环；具体工具与验证对象会变化，完成依据不能丢。

## 复盘：能复用的判断，比一次性的动作留下得久

回看这套设计，最值得留下的是对反馈和上下文的判断：哪些材料决定改动方向，哪些证据能推翻当前假设，哪些卡口必须交回人。

工具也可以在真实任务的反馈中迭代。先补上当前缺少的一种观测，跑起来看哪里卡住，再改进对应能力。工具链本身同样需要验证，不能因为它服务 Agent，就免去这一步。

**让 Agent 取得反馈，才能让它持续修正。** 裁剪动作会结束，确认过的经验和可复用工具却能帮助下一次任务。这是 iLoop 这套循环想长期积累的东西。
