<callout emoji="💡">
**一句话结论：**grok-build 值得看的，不是它作为一个编码工具有多好用，而是它作为一套 Agent 运行基座（harness），怎么解决「会改真东西、要长时间跑、上下文有限、还会犯错」这四个老难题。
</callout>

**调研对象：**xAI 开源的终端编码 Agent grok-build（命令行工具名 `grok`），Rust 编写，Apache-2.0 协议，代码从 xAI 内部 monorepo 定期单向同步（当时 7.5k stars，不接受外部 PR）。

**读法说明：**通读全部 60 多个 crate 的主循环、上下文、工具、子 Agent 和提示词组装后，这篇刻意省去具体函数名、常量和 Rust 细节，只提炼那七条最可迁移的工程判断及其架构落点。

# 这七条设计判断和对应的架构落点

## 按「能不能撤回、波及多大」决定要不要问人

grok-build 决定动作要不要人工确认，只盯两件事：**能否回滚**，以及**影响波及多远**。改本地文件、跑测试放手让它做；删分支、`git push` 覆盖远端或外发不可撤回的消息，必须先征求同意。

> 「确认是廉价的，而一个错误的动作不是。」

更关键一条规矩是**一次批准不作永久授权**：用户这次同意 `git push`，不等于下次情境换了还能自动放行。而在工具实现上，它把「工具能干什么」和「工具有多危险」拆开定义，危险等级直接从类型属性推导，不靠散落各处的 if-else 特判。

<callout emoji="💡">
**反面代价：**确认太碎会打断自动化节奏，因此它也留了用户显式放宽自治等级的开关，把询问集中在真正不可逆的边界动作上。
</callout>

## 按价值梯度回收上下文，而不是等爆了再粗暴截断

模型注意力窗口又贵又有限，长跑过程里的工具日志很快会把上下文塞满。grok-build 把上下文当预算经营，用三条成本由低到高的回收链保住信噪比：

| 回收层级 | 具体做法 | 意图 |
|-|-|-|
| 第一级 | 直接丢弃占空间又低复用的内容，例如陈旧截图和过早的工具输出 | 先省最贵、损失最小的字节 |
| 第二级 | 按规则与年龄裁剪工具中间产物，压低冗余噪音 | 按信息价值降级处理 |
| 第三级 | 快逼近上限时再调模型做结构化摘要压缩 | 花销和信息损失最大，留到最后 |

不管走到哪一级，压缩都要做到**有损但可追溯**：旧详情收走后，真用得上时还得能顺着索引取回来，绝不能把用户原始意图一块儿截没。

## 入口给足、出口收窄：用子 Agent 隔开探索噪音

遇到需要翻大批文件或发散排查的子任务，grok-build 会把它交给异步子 Agent，主循环不直接吞那些试错日志。原仓库里总结成四字口诀：**rich in, narrow out（入口宽、出口窄）**。

子 Agent 拿足完成任务所需的上下文，自己消化探索过程和报错日志，最后只向主线吐回精炼结论。这样主循环既保住了注意力，也顺带做了失败隔离。

## 权限靠结构卡死，不靠提示词自觉

越是放手让 Agent 自己跑，越不能指望靠 prompt 里写「请不要修改文件」来约束。grok-build 对子 Agent 的工具集、操作权限、外部资源和工作区四个维度做了硬隔离。

想让某个角色只读，就在架构边界里直接拿掉写工具，让它想越界也没路子，这比口头叮嘱可靠得多。

## 把计划和进度写进外部文件，防飘移也防假完成

长任务常踩两个暗坑：跑偏忘掉初衷（目标漂移），以及其实没做完却自称搞定。grok-build 把计划、待办清单和状态从模型脑子里拎出来，写成外部可核对的结构化对象。

系统在关键节点直接核验外部证据，不轻信模型口头汇报「done」，既方便人随时盯着看，也能让 Agent 自己及时纠偏。

## 系统提示词和真实能力在构建期自动对齐

不少 Agent 项目写久了会出现提示词和代码脱节：工具删改了，系统提示词还在教模型调旧接口，平白多出幻觉调用。grok-build 把提示词里描述的能力清单直接绑定到当前真实启用的工具集合，并在构建期跑一致性检查兜底，保证认知与能力不漂移。

## 把可打断、可恢复、可协作做成底座默认能力

grok-build 同时支持交互终端、无人值守 CI 以及被其他程序嵌入调用。这靠的是底层两项结构设计：

<grid>
<column width-ratio="0.500000">
<callout emoji="✅">
**分层解耦**
界面层和运行时内核、工具、工作区彻底拆开，才能一套内核跑在交互终端和自动化流里。
</callout>
</column>
<column width-ratio="0.500000">
<callout emoji="✅">
**单所有者串行状态**
会话状态只归一个所有者串行处理命令，省掉锁和竞态，中断、快照和续跑自然干净。
</callout>
</column>
</grid>

用户随时喊得停、状态随时接得上，强能力才敢真的用进生产环境。

# 一张对照表带走这七条判断

| 设计判断 | 它在防什么 | 可直接抄的做法 |
|-|-|-|
| 不可逆性优先 | 承受不起的误删或误发 | 按能否回滚和影响范围判确认；一次同意不作永久授权 |
| 分级回收上下文 | 窗口被日志淹没或暴力截断 | 先删高耗低复用旧产出，再规则裁剪，最后模型摘要且保可追溯 |
| 宽进窄出 | 探索噪音污染主线注意力 | 派子任务时给足上下文，收口时只取回结论 |
| 结构性约束 | 自治权放大后越界失控 | 最小默认授权，能力边界直接写死在工具和权限层 |
| 进度外显 | 跑偏与模型自欺完成 | 把计划和进度存进外部可核验文件，拿证据验收 |
| 提示词即契约 | 提示词过期导致幻觉调用 | 提示词能力清单与真实工具自动同步并进构建校验 |
| 原生可中断恢复 | 黑箱狂奔没法接手或嵌入 | 内核与界面解耦，状态由单所有者串行管理便于快照 |

<callout emoji="🚗">
**整体比喻：**大模型好比引擎，决定跑得多快；harness 是车身、刹车和方向盘，决定这台强力机器能不能安全开上真实马路，且让人敢放手用。
</callout>

# 这套经验的边界在哪里

- [ ] 
  **单一样本限制：**全部观察只来自 xAI 一家团队的开源代码，只能算一种可行解法，迁移前还要横向对比别家方案。

- [ ] 
  **场景绑定：**grok-build 面向终端编码，工作区隔离和不可逆动作的分寸不能照搬去非编码业务，要按新场景重设阈值。

- [ ] 
  **内部全貌未公开：**公开仓库从内部 monorepo 单向同步，一些外围胶水逻辑或内部约束未必全部在开源树里。

- [ ] 
  **每道防线都有成本：**确认太密拖效率、摘要过狠丢线索、隔离太死削弱子任务能力，落地必须在具体场景里做权衡。
