**定位**：AI 管家管理个人工作的全局输入、规划、执行与记录。时间、事情、信息、资料和决策展示同一工作的不同侧面；管家在有效授权内持续推进并保存过程，用户处理必要决策。

内核统一采用 Source、Trigger、Thread、Ticket、Mandate、Assignment 与 Subscription 等语义。下图展示整体分工；这些能力的含义、处理流程和产品扩展均在本文说明。

![个人 Super-agent 总体架构图](/assets/content/ai-butler/img-01.webp)

本方案是目标设计与现有实现的对照。已有能力继续兼容原有身份与历史，不另建一套工单账本；采用 Super-agent 架构不代表已经直接依赖其源码，也不代表所有能力已完成。

# 产品目标与工作流

AI 管家面向个人工作的全局管理。接入工作信息后，管家理解意图、拆解 ToDo 并协调 Agent 执行；时间、事情、信息、资料和决策展示同一份工作的不同侧面，持续接住后续输入与成果。正式产品名称待定，整体方案统一使用“AI 管家”。

下图表达目标工作流：并行执行的成果回到原工作，管家在授权范围内继续推进；需要用户选择时，回答再成为同一工作的后续输入。

![AI 管家持续管理同一份工作的目标流程](/assets/content/ai-butler/img-02.webp)

## 设计来源

最初的起点很朴素：桥接工作人员接收的信息与手机输入，统一规划并行工作、管理执行产物，并通过自然语言与管家协作。

原始表述：“一个工作的不同侧面，或者一个信息的不同维度。”“时间流、事情流、信息流、资料流，都是流的形式。”下面把这些想法归正为产品要求。

## 工作视角

Tab 按用户想了解的问题组织。工作保持稳定身份，换视角时定位同一对象及其关系；浏览不会另建任务、资料副本或完成事实。

| 视角 | 需要回答的问题 | 与其他视角的联系 |
|-|-|-|
| 信息流 | 谁提出了什么；输入已被怎样处理 | 原话、来源与后续反馈，链接生成或更新的 ToDo、事情和决定 |
| 事情流 | 有哪些并行工作；各条主线与分支到哪里 | Group 聚合工作，节点可展开子事项，关联来源、时间、执行和产物 |
| 时间流 | 何时交付；最迟何时开始；现在还缺什么 | 由截止、依赖、可用时间和执行资源规划，关联会议与原事项 |
| 资料流 | 成果在哪里；属于谁；哪个版本有效 | 原件与 Markdown 阅读、工作归属、生成节点、版本和引用关系 |
| 决策流 | 哪些已由管家处理；哪些需要用户选择 | 建议、证据、影响、回答与决定历史，关联受影响的工作分支 |
| 我的一天 | 今天先处理什么；全部并行工作节奏如何 | 聚合当前决策、交付风险、会议和工作图，支持从节点进入各视角 |

## 全局管理与分解

- 输入接入：IM、代码评审、手机委托与想法是首批例子，来源数量可扩展。明确行动意图进入生成或更新 ToDo 的路径，已有工作反馈回到原工作；只记录的信息仍有处理结果。
- ToDo 派发：可由 Agent 执行的工作默认由管家选定执行端并在有效授权内推进。人工、会议和外部等待也进入整体计划，采用各自的推进方式。
- 工作层级：Group 是工作集合；大的工作可继续拆成子工作，叶子 ToDo 承载具体交付。聚合节点汇总状态，实际执行落在明确的任务范围。
- 全局规划：同时掌握各 Agent 进度、用户会议和交付期限。区别用户时间与机器执行时间，识别缺口、依赖和资源冲突；提前交付仍需满足完成标准。
- 上下文取用：全局掌握输入、工作、决定、资料和执行历史，按当前任务装配有效背景。取用继续遵守已有目的、版本与权限边界。

## 贯穿工作样例

目标示例：手机输入“调研 A、B、C，写一份文档，最后形成 coding 成果”。以下说明对象怎样联系；具体并行、前置和截止按这项工作的要求确认。

| 发生什么 | 管家处理 | 视角更新 |
|-|-|-|
| 收到委托 | 保存原话，判断新工作或已有工作补充 | 信息中可查来源与归属 |
| 分解工作 | 形成调研、文档、coding 等 ToDo 并关联大事情 | 事情中可看子工作、分支和依赖 |
| 安排与执行 | 结合截止和资源排期，派给对应 Agent | 时间与运行展示计划及实际状态 |
| 阶段成果到来 | 原工作接收报告，文档和设计稿归入资料 | 节点、资料与当前缺口一起更新 |
| 用户自然语言回答 | 形成新事件和决定，更新受影响范围后继续 | 各视角显示同一次有效变更，保留原始输入与旧成果 |

# 产品与整体架构

管家管理工作的连续生命周期，Worker 处理具体工作。模型负责需要理解的判断，确定性内核负责事实、权限、状态与提交，两者不混为一个无限自主会话。

| 模块 | 负责什么 | 不负责什么 |
|-|-|-|
| Router／管家 | 接住新意图、判断归属、安排、委托、汇总和准备关键决定 | 逐条转发所有工具日志，替每个 Worker 重新规划细节 |
| Engine／确定性内核 | 保存对象，执行准入、版本、去重、依赖、预算与状态规则；作为唯一事实写入入口 | 让模型直接编辑事实库或自行签发权限 |
| Worker／执行者 | 在当前范围内研究、开发、写作与验证，回报进展 | 改写全局目标、扩大授权或创建另一套调度体系 |
| 个人产品能力 | 灵感、事务安排、文件治理、经验与记忆取用 | 把任何收藏都变成任务，把阶段进度当永久偏好 |
| Mac／手机工作台 | 读同一对象、展示有效操作、输入与结果 | 用页面排序、动画或聊天摘要制造完成事实 |

Router 可以承担规则范围内的决策，或让 Worker 整理专业证据再判断；关键目标、费用、外部承诺和授权变化交给用户。无需为了“项目管理＋技术 leader”再增加固定角色进程。

| 执行术语 | 含义 | 在本产品中的位置 |
|-|-|-|
| Executor／执行器 | 内核连接实际执行的接口 | 启动、投递、查询、停止和回传能力各自声明 |
| Adapter／适配器 | 把一个具体系统翻译成统一接口 | ACP、API 或其它执行接法的实现，不是新的管理者 |
| Runtime／运行时 | 实际工具循环、权限与运行环境 | 可复用现有编码 Agent，不重造它们的工具循环 |
| Session／会话 | 某个执行器使用的模型上下文 | 不作为 Ticket 身份、永久记忆或完成依据 |

当前工程沿用桌面原生壳、Web 内容层和本机 Node Core。主脑支持 API 与 ACP 两种方式，当前生产实际连接以设置回读为准；执行侧按真实能力与连接状态启用，不静默换模型。

| 记录层 | 保存什么 | 所有权与恢复 |
|-|-|-|
| 权威事实 | Trigger、Ticket、派工、决定、资料引用、验收及其事件 | 唯一内核写入，沿用已有事件事实；同对象版本与原件可追溯 |
| 索引与快照 | 查询、搜索、阅读投影和缓存 | 可从事实重建；页面状态、索引和模型摘要不成为第二事实源 |
| 原件与备份 | 原始输入、文件、资料版本与历史成果 | 原件先引用，按明确范围备份；不把整个活跃库放入云盘并发同步 |
| 凭据 | 可信连接的账号与密钥引用 | 本机安全入口代用，不将明文交模型或 Worker，不写入任务信封、日志与产物 |

# Super-agent 核心对象与消息流

消息首先成为有来源、可去重的事件，再按讨论归属继续已有工作或评估新工作；收到消息、模型理解、受理、执行授权和成果验收分开。

## 来源、事件与讨论

| 术语 | 解释 | 本产品例子与规则 |
|-|-|-|
| Source／来源 | 持续产生事件的来源实例；保存读取位置和自身范围 | Mac 输入、手机收件、文件变化；每个来源独立授权和恢复 |
| Trigger／事件 | 一条不可变、带来源身份的输入事件 | 一条意见、一份资料更新；同 ID 重放不重复受理。事件可以只记录而不派活 |
| Thread／讨论线 | 来源定义的一组连续相关事件，一个 Trigger 可归入多条讨论线 | 指定一条主 Thread 承接评估，其余补背景或按明确订阅投递；不是网络长连接 |
| Subscription／订阅 | Ticket 与 Thread 之间的多对多关系 | 一个手机研究工单订阅聊天与相关评审；一条讨论可以服务多个工单 |
| Correlation／关联 | 为判断补背景的讨论关系 | 两条讨论相关不等于自动路由，不等于前置依赖 |
| Channel／回传渠道 | 来源的结果写入一侧 | App 结果卡、文档交付、获准的消息回复；读取权不包含外部写权 |

下图表达对象关联，而非一条固定线性执行路径。Ticket 不与 Thread 或 Session 硬绑为一对一，Mandate 可以随工单保存，无需单独制造凭据数据库。

![核心领域对象关系图](/assets/content/ai-butler/img-03.webp)

## 准入、研判与决定

| 术语 | 解释 | 谁做、做什么 |
|-|-|-|
| Policy／策略 | 当前有效的接单、范围、预算和行为规则 | 代码持有版本，模型可提出修改但不自行生效 |
| Gate／准入 | 评估中的确定性检查 | 代码检查来源、身份、重复、范围与运行条件；不合格不进入执行 |
| Assessment／研判 | 需要语义理解的判断 | 模型判断是不是新工作、关联哪件事、如何推进以及未知项 |
| Eval／评估 | 对一批 Trigger 与 Thread 快照进行判断 | 同一 Thread 同时至多一个评估，合并期间的新事件，绑定策略和对象版本 |
| Decision／决定 | 本次评估的结果和依据 | 接单、停止、忽略、未完成；产品另保存必要的备选、采纳与影响 |

稳定、便宜、可明确表达的规则留给代码；需要意图、上下文或专业判断的内容交模型。模型输出仍需校验，没有模型时可以收件和精确登记，不能用机械模板冒充语义理解。

下图展示两条路：已有反馈经订阅直送；没有工作归属的新输入进入评估。越出原范围的要求退回 Router，而不是借订阅扩大授权。

![消息直通与新工作评估流程图](/assets/content/ai-butler/img-04.webp)

1. Source 保存原件、Trigger 与读取位置，核对来源范围，不执行材料中的嵌入指令。
2. 确定主 Thread 及关联 Thread。已有订阅反馈回原 Ticket，同 Trigger 同 Ticket 不重复投递；仅背景订阅不自动恢复已结束工作。
3. 新意图只在主 Thread 进入评估；受理绑定稳定 Trigger ID，不因跨 Thread 重复建工单。多项独立意图明确拆分并留原件血缘，不明归属澄清，只收藏保留记录。
4. 回传 Decision 与有效操作。停止只作用于相关工单，无关工作继续；拒绝或结果未知不被隐藏。

# Ticket、派工与并行工作

Ticket 是一份稳定的已受理工单，状态机规定它怎么变化；Assignment 记录某次由谁承接，Session 只是该次执行使用的上下文。

## 工单与执行分开

| 术语 | 解释 | 保存什么 |
|-|-|-|
| Ticket／工单 | 一项被接受、有明确范围的工作 | 目标、输入、完成标准、Mandate、订阅、历次派工与报告 |
| Mandate／工作授权 | 为什么可接这项工作、允许到哪里 | 授权主体与来源、策略版本、匹配依据、范围、预算及有效条件 |
| Assignment／派工 | Ticket 与某个执行器实例的一次绑定 | 执行器、任务版本、实际运行身份与回执；重试或换执行端新增绑定 |
| Report／报告 | 执行者回到工单的结构化结果 | 进展、等待、就绪、受阻、失败、无需继续；摘要、产物与依据 |
| Attention／待决定 | 需要人作选择的具体问题 | 建议、备选、影响、证据、未知、版本和当前可执行操作 |

“调研手机输入”是 Ticket。执行失败后换 Worker，Ticket 仍是同一项工作；新 Assignment 保留新任务包与回执。Worker 暂时空闲或会话结束，不能直接判工单完成。

下图是产品管理阶段视图，不要求照搬成新的后端枚举。已受理不等于马上执行，待验收不等于完成，停止后的工单不会因普通订阅消息自动复活。

![Ticket 管理阶段与稳定身份状态图](/assets/content/ai-butler/img-05.webp)

一次 Assignment 只经历待启动、执行中、已结束。开始失败、取消和成功都要保留真实回执；结束后重试创建新 Assignment，不把旧实例改回执行中。

![Assignment 一次派工生命周期图](/assets/content/ai-butler/img-06.webp)

## 个人事项与关系扩展

| 产品对象或关系 | 语义 | 与内核的关系 |
|-|-|-|
| Goal／事情或专项 | 目标与多项工作的稳定集合 | 保留现有 Goal 身份，聚合多个 Ticket；不是 Thread 或另一种执行工单 |
| 人工／外部／提醒事项 | 可安排但不必调用 Agent 的工作 | 记录实际推进方式和结果，无需伪造 Worker 或 Run |
| parent／归属 | 包含、工作拆分 | 容器只汇总，不重复派发，不代表先后 |
| relates／相关 | 工作或材料有关联 | 不阻塞、不自动续办，不能替代 Subscription |
| blocks／前置 | 标准满足以后才放行下游 | 检查依赖与循环；父子不冒充前置 |
| 派生分支 | 某个想法或结果引出另一项工作 | 保留来源节点；新的范围单独受理，并非要求主线等待 |

![主线与独立支线的并行分叉图](/assets/content/ai-butler/img-07.webp)

安排依据用户约束、截止风险、前置价值、个人时间、资源与费用，附理由并可调整。截止、最早开始和占用时段分开，未知时间与负责人不猜；共享工作区、文件和外部资源按实际冲突串行。

# 个人管家产品扩展

Super-agent 提供持续接单与工作归属的内核，个人产品还需接住不执行的信息、长期事务、资料和记忆；扩展以字段、策略、来源及视图承载，不另造一套任务循环。

## 灵感、资料与记忆

| 输入 | 默认处理 | 升级为工作的条件 |
|-|-|-|
| 碎念、日记 | 本地保留原话，不推导永久性格 | 用户明确要求行动；不因情绪描述自动派活 |
| 灵感 | 暂存、分类、建议关联 | 目标、推进意图与允许范围明确后形成工单候选 |
| 知识、链接与文件 | 保留出处或原件 | 获准理解、关联或委托；收藏不自动抓取、解析或外发 |
| 偏好、经验与方法 | 记录来源和提议 | 确认范围后写个人记忆或工作规则，审批历史不等于新授权 |
| 行动、研究与日程 | 查原事情与已有工作，给可编辑候选 | 受理、方式、资料与条件明确；确认保存不自动派发 |

Material／资料保存内容身份、位置、版本和用途；一个原件可被多个工单引用。目录、摘要、原件、草稿、阶段成果、有效结论和历史版本分别表示，不以文件名或修改时间猜有效性。

| 记忆来源 | 保存内容 | 使用与更新 |
|-|-|-|
| me-context 及已确认个人记录 | 稳定事实与偏好 | 按目的、受众和本地边界取用；纠正、撤回或事实变化时更新 |
| 事情与工单档案 | 目标、决定、阶段、问题与成果 | 用当前有效版本，历史进度不升级为永久个人事实 |
| 经历与验收 | 失败、纠正、取舍与证据 | 相似任务按需找回；有效且确认后再提议规则 |
| 灵感与知识 | 未证实观点、素材与原件 | 可暂缓、归档和重分类，不默认成为工作或事实 |

Inline／窗口内摘要是当前必要卡片；Spill／窗口外保存是长材料原件；Chain of Recall／引用召回沿 ID 逐步找回背景。它们帮助找到材料，但正确性、有效版本和取用权限仍要核对。

下图明确“保存”和“取用”的区别。Thread 订阅、资料复制和目录权限不能把本地原件变成允许外发的上下文，摘要不覆盖原文。

![个人记忆与资料取用数据流图](/assets/content/ai-butler/img-08.webp)

## 人设、管家守则与关于我

设置分成三层：人设决定表达和相处方式；管家守则决定长期做事方式；关于我来自 me-context，提供沟通偏好、工作、目标和决策偏好四类背景。三者分开保存，避免把一次任务要求、资料正文或临时情绪写成永久人格。

| 配置 | 作用 | 写入与取用 |
|-|-|-|
| 人设 | 表达风格、称呼、语气 | 用户可编辑并持久保存；主脑提示携带，执行信封保留同一约束 |
| 管家守则 | 长期做事方式与边界 | 只接受本人最新消息中的明确长期要求；带启用状态、原输入、版本与修改记录 |
| 关于我 | 稳定背景、偏好和目标 | 从 me-context 四个白名单域按用途读取结论层；仅本机或未授权内容继续由原门禁阻断 |
| 模型 | 主脑判断与执行端能力 | 读取本地模型服务的实时目录，主脑与执行端独立选择并精确回读；合法模型不因默认模型缺失而被拒绝 |

模型目录按实时接口读取，主脑与执行端分别选择，适配层过滤上游的固定元数据警告，不进入判断正文。日历按任务生成稳定的六种淡色，日、周、月共用同一色序；浅色和深色分别定义对比度，状态、截止和最早开始仍保留语义样式。

设置中的“关于我”打开独立二级弹层，直接读取 me-context 生成的 HTML 总览，显示关系网与档案；原读门禁和云端取用边界不变。人设默认只读，点击后编辑；管家守则改为整段编号编辑。AI 管家发送后显示处理状态流，候选摘要逐字出现，输入区只保留发送按钮。关闭按钮始终可用，关闭不取消后台判断，顶部入口显示运行点，重新打开继续看到同一进度。我的消息在左，管家回复在右；连接建立后显示当前模型名。

## 工作记录与总结写作

工作流同时形成可追溯的工作记录。按事情、时期或主题重建原始输入、决定、推进过程、时间和成果，支持项目总结、技术文章和文档写作；资料与事件保留出处，阶段事实不自动变成永久个人偏好。

| 记录内容 | 需要保留 | 写作时怎样使用 |
|-|-|-|
| 原始输入与目标 | IM、邮件、代码评审、平台入口与手机原话，来源及实际时间 | 还原为什么开始、当时约束和目标变化 |
| 推进与时间 | 拆分、依赖、派工、尝试、阻塞、失败、阶段结果和验收 | 分清计划、尝试和实际完成，复原阶段过程 |
| 决定与取舍 | 用户或管家的选择、依据、影响、策略版本与后续纠正 | 解释为什么这样做，以及后来怎样修正 |
| 资料与成果 | 文档、Markdown、设计稿、代码及其版本、生成任务和用途 | 找到可引用的原件、数据与有效成果 |
| 写作取证 | 来源记录、Agent 报告、核验结果分别标明 | 关键数据和结论能回到证据，缺失记录保留未知 |

例如总结一次专项：沿原事情找回最初需求、方案演进、调研、设计稿、coding 成果和实际验证，再组织成文章。记录服务于回顾与判断，文章结论应与当时证据和当前有效版本对应。

## 本次资料取用上限

此处是当前主动输入与选定资料进入模型的限制，不是资料库总量限制；目录可以保存更多文件，但每次判断必须明确选取。

| 限制 | 当前值 | 计算与失败处理 |
|-|-|-|
| 本次资料选择 | 最多 8 份 | 请求最多 8 个资料 ID；9 份明确拒绝，不自动替用户删除一份或读未选材料 |
| 完整判断上下文 | 最多 200000 字节 | 按完整序列化证据的 UTF-8 字节数计算，包含消息、选定原文、对象与契约等；不是字数或 token 数 |
| 较小的请求预算 | 可低于上限 | 上下文预算可以更小，不能高于 200000；完整证据超过本次预算即拒绝 |
| 私密或未授权资料 | 只取本次明确允许部分 | ID 关联不等于模型许可；撤权、版本变化或未勾选内容不能因预算尚有空间而加入 |

超预算保留已保存原话，返回明确错误，要求缩小资料或明确分段；不调用模型、不生成替代候选、不新建 Run，不默截、换模型或无限放大预算。资料变化后重新核对许可与当前版本。

边界验收覆盖 8／9 份、200000／200001 字节、中文与 emoji 的 UTF-8 计量；相同字符数量不能替代实际字节检查。

- **资料治理**：先逻辑分组、检索、原件阅读和反向引用。搬移、重命名或删副本须独立预览链接、运行工作、备份与外部引用影响。
- **内容解析**：文本与 HTML 安全解析先行，不运行嵌入脚本或远端资源；未读懂附件仍保存原件并标范围。
- **规则维护**：有来源、适用范围、版本与撤回入口；记忆提议不由模型自动写回，纠正不静默改掉历史证据。

## 主动管理与智能决定

| 情况 | 管家如何推进 | 停止或上交 |
|-|-|-|
| 材料不足 | 允许范围内找已有资料或有限补证 | 没权限或关键事实未知，不反复要求用户重讲全部背景 |
| 后续意见到来 | 更新原 Ticket 背景与受影响版本 | 超出原范围退回评估，旧批准不用于新内容 |
| 需要选择 | 准备一个持续有效的 Attention 包 | 目标、重大期限、费用、外部承诺与授权变化交用户 |
| 结果不合格 | 区分执行、资料和验收问题，必要时重验文件 | 不一律重做，不无限追加无关验收 |
| 环境、权限或登录缺失 | 保存明确阻塞与恢复条件 | 不换工具绕拒绝，不无限派发 |
| 无进展或失联 | 有限核对真实状态 | 能力不足、预算或重试耗尽时保存进度并停相关分支 |

主动规则先 observe／仅观察，记录“会做什么”但不执行；auto／获准自动处理仅在明确范围内生效。安静时段延后普通提醒，允许的准备和无关工作继续，无新事实不反复调查或打扰。

Attention 回答当前工作和版本、建议与备选、影响、证据及未知项。关键决定和工具许可关联但分开，模型自信不能替代有效授权。

## 决策首屏

决策首先告诉用户现在需要做什么。首屏按固定顺序呈现，详细原文、引用和过程可继续展开；自然语言回复与选项具有同等地位。

| 首屏信息 | 表达要求 |
|-|-|
| 我要决定什么 | 一句话写清当前问题或需要做的选择 |
| 隶属于什么 | 显示事情、节点及当前问题，归属可点击继续阅读 |
| 关键上下文 | 只列会改变决定的事实、限制和缺口，提供原文与资料入口 |
| 推荐与备选 | 明确推荐哪个选项及原因，备选说明主要代价，不强凑固定数量 |
| 我的自由回复 | 允许直接用自然语言给新要求，绑定当前工作、问题和版本 |

## 授权策略与夜间推进

用户预先设定可代理范围，管家在夜间按当前有效策略处理允许的选择。用户离线不改变红线；需要本人决定的操作保存阻塞与恢复条件，其他获准工作继续。

红线在派工和工具执行入口强制校验，夜间策略不能覆盖。管家处理选择时仍须核对当前范围、版本及执行端能力。

| 策略类别 | 管家可以怎样处理 | 需要留下什么 |
|-|-|-|
| 仅观察 | 记录建议与预计动作，等待明确许可 | 建议、证据、未知及等待原因 |
| 预授权代理 | 在指定动作、工作范围、预算、时段与有效期内处理可回退选择 | 选择、依据、权限来源、动作结果和实际回退方式 |
| 本人确认／红线 | 上线相关确认等红线操作始终留给用户，暂停相关任务或分支 | 具体待决问题、上下文、建议及继续条件 |

- 策略登记：操作类别、适用工作、工具与资料范围、时段、预算、有效期和撤回方式明确。新增范围不能由模型自行批准；执行端拒绝或平台权限不足继续按原边界处理。
- 回退依据：可代理动作须有真实撤销或恢复方式。执行前保存必要版本与状态，撤销后核对实际结果；回退产生新记录，保留原决定和已发生效果。无法确认可回退时留给本人。
- 夜间推进：允许的选择可自行处理，遇红线只停相关分支；次数、预算耗尽或结果未知时按规则停止，避免重复派发。
- 次日汇报：分别展示已代理处理、需要重点复核、红线仍等待的事项。说明选了什么、为何这样选、影响与回退入口，普通结果无需逐项重新审批。

日常入口据此组织：汇总办公软件、邮件、代码评审和组织平台输入，展示今日工作、会议、交付风险与 Agent 状态。用户处理必要决策并检查整体调度，管家承担已授权的日常整理、跟进与协调。

## 效率与日常流程

排队、执行、请求答复、验收等待、失联、返工和人工投入分别统计，按 Ticket／Assignment 身份配对，重叠等待取并集。缺事件留未知，机器时长不当人工工时。

- **样本边界**：历史事件里的环境类失败只能说明现场情况，数量不能证明触发方式或当前故障；核对失败类型、停止条件和人工协调、审阅与交付接受率。
- **固定流程**：保存模板、触发、资料范围、预算和输出，各次执行独立去重。草稿与发布分开，外发核对接收方、版本、许可与回执，不重复发送未知结果。

# 异步、恢复与手机电脑互联

持续工作需要把动作、结果和恢复从模型会话中拿出来；手机是同一体系的输入与操作端，不另建 Ticket 数据库，也不因远控增加授权。

## 动作保存与异步执行

| 术语 | 含义 | 必须区分 |
|-|-|-|
| Effects／持久动作队列 | 提交后要执行的动作，含身份、状态和重试依据 | 记录了动作不代表已发生外部效果 |
| Outbox／待发箱 | 等待可靠投递的消息或结果 | 手机本地待发箱、服务端动作队列和结果回执是不同位置 |
| Receipt／回执 | 某一步真实受理、投递或执行的结果 | 受理、投递、执行、验收各有回执，不能互相替代 |
| history／seq | 内容版本与事件序号 | 重连按游标补读，历史变化重新取快照，不能用总条数判断同内容 |
| Watchdog／独立监督 | 观察存活、进展与异常的机制 | 活着不等于有效推进；有限核对，不自动装全局常驻监控 |

下图表达目标提交语义：必要事实与待动作可靠保存后才执行。当前跨事件部分保存机制不冒称数据库事务；复用开源 Engine 或 Effects 时，只保留一个事实写入者。

当前主脑的 intake 由 Core 托管单次判断，HTTP 只启动和查询。同一会话及相同请求复用同一 job；丢响应或短断后先查询原结果，不换请求重复派发。候选继续使用原来源、版本和权限校验。

job 状态保留在当前 Core 进程，完成记录定时清理；原输入和已生成候选仍保存在事实库。关闭面板或主窗口不停止判断，明确退出 App、休眠和 Core 重启的运行边界分别保留；当前不包含跨进程恢复、持久动作队列或外部效果补偿。

![异步动作与结果未知恢复流程图](/assets/content/ai-butler/img-09.webp)

- **幂等**：同命令 ID 同内容回原结果，异内容拒绝；失败或丢响应先查原命令，不换键制造替代动作。
- **恢复**：先重建记录，再装配当前背景，再核对执行器与外部效果。Git 同步、云备份或复制 session ID 不能代替运行接续和多节点排他。
- **续办**：新反馈可继续原 Ticket，但核对意图、版本、权限与已发生效果。停止后不自动恢复；旧验收与产物保留，变更只影响相关工作。
- **撤权**：策略变化使未应用研判失效，普通变更保留现场并核对后续动作；紧急取用或操作撤权立即阻断相应权限，不只通知模型“别做”。

原型使用集中本地部署与 SQLite，文章提出运行、状态和环境分离。本文可沿此方向扩展云端，但没有把原型写成现成云备份或跨设备执行服务；当前退出、休眠或离线的本机不能继续实际干活。

## 手机交互

Hub／连接中心负责设备连接、鉴权和消息中转；Node／电脑接入节点连接实际执行环境。它们属于部署方式，管理语义仍由同一内核掌握，角色不等于必须拆成几个常驻进程。

下图把私密收件、明确委托、关键决定与结果验收分开。同一 Ticket 在手机和 Mac 回读，重复或过期回答不能重复执行。

![手机收件与委托确认时序图](/assets/content/ai-butler/img-10.webp)

| 路线或参考 | 结论 | 采用边界 |
|-|-|-|
| 系统快捷指令 | 最轻的首轮收件候选，传专用包 | 不同步活跃事实库、索引、凭据或完整档案；校验消息 ID、附件、离线和回执；手机实测尚未通过 |
| Persona | 可借原生采集、落盘待发队列、同会话结果与交互卡 | 独立 Hub 与 Persona 协议；分享扩展不等同聊天的离线保障，不能改地址就接本 Core |
| T3 Code | 可借多执行端远控、设备配对、命令回执和事件恢复 | 手机到服务器是 HTTP／WebSocket 与隧道；服务器到 Agent 可用 SDK、app-server 或 ACP，不是统一 ACP |
| AgentDock | 可借会话／轮次观察、状态依据、跟进去重与撤销 | 观察有启发式；“已处理提醒”不当 Ticket 验收，不接成第二调度器 |
| Personal Harness | 方法装配与执行 Runtime 可复用 | 不作为所有任务必经层，建议或外部会话状态不代替当前授权和完成事实 |

ACP／Agent Client Protocol 是执行接入协议；REST／WebSocket 是客户端与服务端的通信方式；VPN／隧道解决网络可达。它们都不能单独保证材料入库、权限或业务完成。

正式远控先验证非敏感输入保存回执，再验证同 Ticket 结果和决定；执行器拒绝就停止，不走另一条工具路径绕过。设备令牌、TLS 与必要的有效期单独核验，公网或模型外发权限不从“本机程序”推断。

# Mac 工作台与产品设计

页面承载同一份工作的不同视角，关系与阅读历史把这些视角串成流。界面使用“事情、事项、资料”等自然名称，内部对象保持稳定身份；每个视角都能定位原工作、来源和成果。

| 页面 | 阅读任务 | 对应内核 |
|-|-|-|
| 我的一天 | 当前决策、交付风险、会议与全部并行工作的节奏 | Ticket、Attention、Report 和安排属性 |
| 决策 | 待用户选择、自主处理结果、理由和决定历史 | Decision、Attention、Report 与有效版本 |
| 日历 | 占用、截止、最迟开始、待排工作与交付缺口 | 工作时间属性，不编造未知时长或完成时间 |
| 事情 | 看专项、独立事项、主支线和局部过程 | Goal 集合、Ticket 及类型明确的关系 |
| 信息 | 原话、来源、处理去向与生成或更新的工作 | Source、Trigger、Thread 与采纳状态 |
| 资料 | 目录与关系图阅读，生成来源、版本、关联和反向引用 | Material 与有效上下文，不复制多份知识库 |
| 运行 | 调度、执行端、运行、等待、产物与异常 | Assignment、Executor、Report 和真实回执 |
| 设置 | 阅读、材质、连接、安全与调度 | 本机偏好、Policy 和能力声明 |

## 工作图与并行总览

图用于呈现工作关系和并行节奏，文字说明节点含义与当前问题。首页看全局，事情页看选中工作的局部图，节点详情继续展开；资料可从目录或关系图进入同一正文。

| 设计要求 | 表达方式 |
|-|-|
| 全局与局部 | 总览按事情或工作分支分行，突出当前节点；选择后展开局部关系，保留其它并行工作的定位 |
| 节点语义 | 区分工作集合、子工作、具体 ToDo、事件、决定与成果；大节点可聚合，详情能查看子任务、执行者和剩余工作 |
| 关系语义 | 分别标明归属、派生、前置与成果采纳；分支从真实来源切出，明确登记后才显示汇合 |
| 时间含义 | 事情图横向表达过程顺序；时间图使用真实时间轴。估算、未知结束和实际完成分开显示 |
| 完成状态 | 执行结束、产物提交、工作验收与分支成果采纳分别表达；汇总状态可继续展开到证据 |
| 资料关系 | 以当前资料和关联工作为焦点展开局部图，保留正文阅读、目录检索和文件身份 |

## 跨维度导航

两种呈现方式共用对象详情、关系链接和阅读历史。阅读路径记录从哪里进入；业务归属说明对象属于什么工作，两者分别展示。当前原型已增加决策 Tab，首页保留当前需要处理的决策摘要。

| 方式 | 最强收益与适用条件 | 代价与保障 |
|-|-|-|
| A：逐层打开二级页 | 从一个问题追到事情、时间、来源和资料，适合围绕同一工作持续阅读 | 需管理路径与返回状态；内容区逐层进入，返回恢复对象、图位置、筛选和滚动位置 |
| B：定位到对应 Tab | 直接使用完整视角，适合频繁切换不同事情或批量处理 | 容易丢失当前焦点；跳转选中目标对象，保留工作上下文和上一站入口 |

产品默认采用 A：关联内容以二级页逐层进入，后退回到上一级，前进恢复后续阅读。B：定位对应 Tab 作为可切换方式保留。两种方式共用内容与对象关系；后续验证围绕路径、焦点和返回状态，不重新把默认方式当作未定项。

- 连续阅读：决策→所属事情→相关时间→信息来源→资料，关系存在就可继续进入，逐层返回到原位置。资料多归属时列出明确关系供选择。
- 统一入口：同一节点提供相关事情、ToDo、时间、信息、资料、决定与运行的可用入口，缺失关系显示当前缺口。切换呈现方式不改变对象身份。
- 返回与刷新：保留阅读历史及每个视角的定位；后台更新维持当前焦点。阅读路径不能被保存成新的父子或依赖关系。

## 自然语言决定与更新

用户在当前决策或节点内用自然语言回复管家。回复绑定当前工作、问题和版本，成为新事件；管家理解变更，再由内核校验和提交。图与各 Tab 回读同一变更，不单独修改图形来制造状态。

| 环节 | 需要让用户看清 |
|-|-|
| 提出调整 | 当前针对什么工作、问题和版本，原话可回读 |
| 理解与影响 | 哪些 ToDo、期限、依赖或分支会变化，建议依据及仍未知的内容 |
| 应用决定 | 已有授权内执行，歧义或越界只询问必要问题；保留有效决定与旧版本 |
| 继续推进 | 说明已更新什么、哪些 Agent 继续、什么仍等待；图和其他视角一致反映结果 |
| 自主处理 | 管家可自行承担的决定保留结果与理由；需要用户判断的问题集中进入决策视角 |

## 视觉层级与状态颜色

保留冷色磨砂材质，阅读区域使用稳定衬底。通过位置、字号、字重和高对比色面突出当前问题、推荐动作、截止与状态；来源、历史和过程信息退到次级，仍保持可读。

| 视觉对象 | 建议表现 |
|-|-|
| 当前决策焦点 | 主问题明显大于队列标题，推荐动作突出；首屏能辨认需要做什么、所属事情和推荐 |
| 重要截止与红线 | 用醒目的期限、状态标签和必要色带标出，避免只靠很浅的行底色 |
| 工作图当前节点 | 节点与状态标签共同突出，已完成、运行、等待输入和待用户决定可以快速区分 |
| 状态语义 | 建议逾期或失败用红、待本人决定用紫、缺输入用琥珀、运行用亮蓝、完成用绿、未开始用中性灰 |
| 状态跨视角 | 列表、图节点和二级页使用同一含义，并保留状态文字；代理审批记录另标处理者和是否需要复核 |
| 普通信息 | 正文和来源有字号、字重、间距与衬底差异，保持主次而不削弱阅读 |

后续视觉迭代重点是扩大关键状态的辨识面积、突出一个当前焦点，并在所有视角保持一致；具体色值和字阶继续通过画面确认。

## 阅读与交互规则

- **判断焦点**：当前问题与候选队列分区，避免每行同等醒目的按钮；关键时间、状态、建议和依据清楚。
- **专项与分支**：紧凑索引选择事情，只展开局部流程；分叉直接连接来源节点，派生与前置线型、说明分开。
- **信息与角色**：列表标题和副标题各一行；用户、助手与系统记录分清，过程日志不抢正文。
- **资料阅读**：目录、正文和局部关联图独立滚动，身份、原件与版本可定位，统一前进后退历史。
- **执行状态**：身份图标与状态灯分开，只有真实运行状态适度活动；进程存活不当完成。
- **平台**：按 macOS 窗口、侧栏、工具栏、菜单、快捷键和材质验证；自然语言判断、精确登记、保存与执行分开，后台刷新不抢焦点。

# 实现边界与验收

目标语义与现有实现之间采用兼容映射，不为了名称重建账本。映射是对旧事实的兼容解释，不是重新受理全部工作：先检查结构，再查受理依据，最后独立核对验收与当前授权；名称、时间戳、todo、done 或验收字段不能单独证明受理。

| 现有实现 | 采用的 Super-agent 语义 | 仍需补齐 |
|-|-|-|
| 输入与来源记录 | 保留原件，转换为 Source／Trigger | 持续来源游标、明确 Thread 归属和投递去向 |
| 多轮会话与关联 | 复用输入，增加 Thread／Subscription 语义 | 会话不等于讨论订阅，重复反馈不能重复受理 |
| Task／Goal | 已受理叶子 Task 承载 Ticket，Goal 聚合工作 | 草稿、收藏、容器、受理、执行许可与验收分别表示 |
| Run 与任务信封 | 关联 Assignment 与实际会话 | 派工、尝试、进程和 Session 不混同；旧 ID 不重建 |
| 规则、审批与版本检查 | Gate／Policy／Mandate 的依据 | 完整工作授权及持续反馈范围，不拿日志当凭证 |
| 状态投影与管理决定 | Ticket／Report／Attention | 自动准备待决材料、识别交付与下一步，仍缺完整运行验证 |
| 幂等命令与部分恢复 | 为 Effects／Outbox 提供现有基础 | 可靠提交与外部结果对账，不冒称已经实现事务动作队列 |

历史对象按证据分级处理：只有输入或资料、没有受理依据的，保留为候选；有可信受理记录的，沿用原身份并补当前授权；旧验收与完成证据分开保存，不把已完成改成待办，也不伪造通过。补受理或授权使用原对象 ID，在同一事实日志保存确认依据；用户明确修订范围时才产生新版本。

除以下执行边界外，产品验收还需证明同一工作的来源、分解、并行推进、时间和成果能连贯回读。

| 产品场景 | 通过条件 |
|-|-|
| 输入转工作 | 可从 IM／代码评审／手机原话定位生成或更新的 ToDo，并查对应事情与派工结果 |
| 全局并行图 | 用多条主线及分支样例查看当前节点、执行者和剩余工作；单个事项与多层工作都能继续展开 |
| 交付规划 | 同看会议、待排工作、截止与前置缺口；提前交付建议附估算依据和未知项 |
| 连续阅读与返回 | 从决策经事情、时间、来源到资料，再逐层返回；对象、图位置和筛选保持正确 |
| 自然语言调整 | 修改一个分支后各视角同源更新，原话与旧决定保留，无关分支继续 |
| 资料归位 | Agent 产物能反查生成任务、所属工作、版本和用途；多归属指向同一原件 |
| 工作记录与写作 | 按专项或时期找回输入、决定、推进与成果，文章关键数据和结论可回到原件及核验记录 |
| 夜间预授权 | 白名单范围内的选择可代理，记录依据与结果；上线等红线只停相关分支，普通获准工作继续 |
| 真实回退 | 允许的可回退操作有实际撤销方式与回执，恢复后核对状态，原决定和历史效果保留 |
| 次日工作台 | 区分已代理处理、重点复核和红线等待，说明选择、影响及回退入口 |
| 决策与视觉 | 首屏可辨认当前问题、所属事情、关键状态和推荐；可自然语言回答，状态语义跨视角一致 |

| 场景 | 通过条件 | 应拒绝的结果 |
|-|-|-|
| 手机一条灵感 | 私密原文和回执一致，可只记录零 Ticket | 收到即执行或未经许可发模型 |
| 主线运行时补支线资料 | 找到原 Thread／Ticket，材料关联有出处，无关工作继续 | 新建重复工单或冻结所有工作 |
| 原 Ticket 收到新范围 | Worker 退回 Router，新的受理与授权明确 | 以订阅或旧批准扩大范围 |
| 执行中追加意见 | 输入进入下一步并保留版本，原 Assignment 结果可核对 | 旧上下文产物无声覆盖新决定 |
| 回执丢失与重启 | 原命令回读，对账已发生动作，未明状态不盲重派 | 复制会话 ID 称恢复，重复外部写入 |
| 交付与人工决定 | Report、产物、Attention 和有效选择同源 | 最终回复、已读或提醒划掉等于验收通过 |
| 资料变化、撤权或过期候选 | 旧判断不应用，历史保留，受影响背景重核 | 缓存绕过撤权或修改历史原文 |

<callout emoji="💡">
**阶段判断**：已有能力可以继续复用，不需要为了 Ticket／Assignment 名称重建账本；差距主要在持续管理路径，不在页面数量。每项完成状态以原对象、业务回执和验收为准，不以界面勾选或测试条数代替。
</callout>

实施优先补“新输入归属与续办”和“补证、待决、结果回流”两条管理路径；手机收件与远控按独立边界验证，不拖住 Mac 视觉主线。结果以减少补背景、切窗口、漏项和人工协调来评价，阶段成功不缩小长期目标。
